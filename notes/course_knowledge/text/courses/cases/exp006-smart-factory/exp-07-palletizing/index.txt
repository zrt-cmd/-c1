EXP-07 · 第 2 章 · 综合性 · 6 学时
自主码垛：流水线送料 + 跨节点编排抓取
码垛是全项目最完整的任务链路：N2 调度器先调 N-conveyor 的 run_until_sensor 让流水线送料
    （复用底盘电机 M1，光电 GPIO17 定点停），订阅 /eai_factory/conveyor/state 收到 sensor_blocked 后
    才触发 N-grasp 固定点位八步抓取，完成后播报"码垛完成"——融合流水线驱动、光电防抖、跨节点状态同步三大知识点（R6）。
🏗️ 跨节点编排
M1 电机复用 · rps=0.1
光电定点停 run_until_sensor
sensor_blocked 状态同步
急停置位保持 · 显式复位
01
问题引入：为什么要"先送料，再抓取"？
分拣是手边直接抓，码垛的物料却在流水线那头——这引入了两个新问题：
流水线怎么停得准
（不能靠数秒数），以及
两个节点怎么配合
（调度器不能瞎猜物品到了没有）。源讲义的回答是：让传感器说话。
    流水线转到光电被遮挡才停（
sensor_blocked
），调度器订阅这个状态、收到才触发抓取——
用状态同步取代 sleep 固定时长
，这是分布式编排的通用范式。
相应地停不准也有代价：本实验快速验证流程里写得很清楚——触发后不放物品，送料会空跑
sensor_timeout=30.0s
后置
timeout
，抓取永远不会开始。
02
原理通俗讲解：传送带、感应门与调度室
借马达
流水线电机复用前左轮
工厂流水线不另买驱动，
复用底盘电机通道 M1（前左轮）
：N-conveyor 往
/car1_base_driver/set_motor
发速度，STM32 会
保持最后收到的速度一直转
；
        要停就发
rps=0
——立即且可靠。参数：
motor_id=1
、
run_speed=0.1
（m/s）。
        就像借用已有的电风扇插座：插上就转，拔掉（发 0）就停。
感应门
光电四段式定点停
run_until_sensor
分四段：
先等"清沿"
（光电恢复无遮挡，确认起始端干净）
        →
再等"挡沿"
（物品到达、电平变 LOW(0)）→
防抖确认
（
debounce_reads=3
连续 3 次读遮挡才算数，
poll_period=0.05s
）
        → 停带。约定：
1=无遮挡、0=遮挡
；超时
sensor_timeout=30s
。
        就像车库感应门：先确认门前确实有车、稳定停住，才判断"到位"。
调度室
等状态，不数秒
N2 的
_start_palletize_sequence
（L98-110）置
_awaiting_sensor=True
后异步调送料；
        物品到位时
_conveyor_state_cb
（L121-127）收到
sensor_blocked
才
_trigger_grasp('palletize')
。
等信号，不等时间
——传送带快慢、物品长短都不影响正确性。
保险栓
急停置位保持、显式复位
conveyor 状态机：
idle / running / sensor_blocked / emergency / timeout / error
。
emergency_stop
置位
_emergency_stop=True
并立即发 rps=0（L240-248）；
        期间
run
/
run_until_sensor
一律拒绝（"emergency active — call reset_emergency first"），
        必须显式
reset_emergency
才回 idle——
急停后绝不自动复跑
，像总闸按下后必须人工合闸。

04
实验目标
理解复用底盘电机 M1 的驱动原理（发布速度 → STM32 保持 → 发 0 即停）与光电电平约定 1=无遮挡、0=遮挡。
掌握 run_until_sensor"清沿 → 挡沿 → 防抖 → 超时"四段式流程与流水线状态机转换。
独立完成"先送料后抓取"跨节点编排的全链路验证（服务/语音双通道触发，观察 sensor_blocked → 抓取 → done）。
掌握急停置位/复位语义与 run 被拒绝的安全含义，能按 docs/10 完成 TC1~TC9 验收。

重点与易错点
诊断
"只送不抓"三查：
state 到没到 sensor_blocked
（photo 话题是否 true）、
防抖满足没有
（debounce_reads=3）、
急停标志在不在
（emergency 拒绝返回）。
现象
根因
处理
流水线不转
GPIO 未导出或电机通道接错
sudo bash scripts/setup_conveyor_gpio.sh
；确认 conveyor.motor_id=1
run_until_sensor 立即 timeout
物品已停在光电位，清沿不满足
先移开物品再触发，或先 run 清位再 stop
遮挡了仍不判 sensor_blocked
电平约定弄反或防抖未满
确认 1=无遮挡、0=遮挡；看 photo 是否持续 true 三个周期
码垛只送料不抓取
state 变化没触发 _conveyor_state_cb
ros2 topic echo /eai_factory/conveyor/state
确认消息在发
抓取位置偏
堆叠高度/位置与打点不一致
重新打点更新 grasp.tasks.palletize.observe_pose（yaml L89）
服务一直拒绝 "emergency active"
急停置位保持，未显式复位
reset_emergency
后再触发（安全设计，非故障）

10
总结与思考
借力
M1 电机复用
发速度即转、发 0 即停，STM32 保持最后速度驱动流水线。
等信号
清沿→挡沿→防抖→超时
四段式定点停，debounce_reads=3 过滤抖动，30s 超时兜底。
跨节点
state 同步再抓取
_awaiting_sensor + _conveyor_state_cb，状态驱动取代定时。
安全停
置位保持 · 显式复位
急停后 run 全拒，防误自启是设计而非缺陷。
思考 1
为什么 run_until_sensor 要先等"清沿"再等"挡沿"？如果物品一开始就在光电传感器处，
      省掉清沿会发生什么？（提示：与超时 30s 现象联系起来）
思考 2
编排等待如果不用 _conveyor_state_cb 订阅、而是
sleep(10)
再触发抓取，
      在"传送带加速"和"抓取服务还没就绪"两种情况下分别会出什么问题？
      结合 _pending_task / 2s 重试机制说明状态订阅方案多补了哪一层保险。
