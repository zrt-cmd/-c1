事件日志与故障降级：坏了也不能崩，事后还能查
边缘 AI 设备 7×24 跑在真实环境里，断网、拔相机、杀播放器是常态。本实验两条主线：
事件日志

01
问题引入：出事了，谁的锅？
前面的实验都在"一切正常"的前提下验证功能。真实部署会遇到：
1
目标跟丢了——
什么时候丢的？是出画还是跟踪器提前放弃？
没有记录就无法回答
2
锁定莫名其妙解除了——是用户说了"清除"，还是 unlock_on_loss 全丢自动解？
两种路径要能区分追责
3
用户说"追踪一百号目标"——id=100 根本不存在，此时
锁一个差不多的？解锁当前的？还是什么都不做？
4
断网了 LLM 连不上、ReID worker 全崩、aplay 被杀、相机线松了——
主循环绝不能崩、不能挂起
5
LLM 指令处理期间主循环暂停读帧，若 LLM 挂死——
画面冻结 30 秒后谁来解冻？
⚠️ 两条设计红线
① 状态变化必须留结构化痕迹（events.jsonl）供事后追责；② 任何"不确定"分支
零副作用
，全部故障都有收敛策略——这就是 fail-closed + 降级。
02
原理通俗讲解：黑匣子与各退一步
比喻 1
events.jsonl = 飞机黑匣子 + 值班日志本
每发生一件"有状态意义"的事（锁定、跟丢、解锁、断流、超时）就
追加一行 JSON
，永不改写历史。就像黑匣子只记录不辩解：tail -f 实时看、jq 逐行查。写失败也只吞异常——
日志系统自己绝不能把主程序弄死
。
比喻 2
fail-closed = 拿不准就不盖章的银行柜员
柜员办业务时身份证对不上，规范做法是
"退回材料，不盖章也不涂改"
——宁可这单不办，也不能盖错章。对应代码：所有 fail 分支的共同点是
不调用 engine.submit_effect()
；锁是印章，只在完全确定时落下去。
比喻 3
空 submit = 误会也会毁约
有人问"追踪一百号"，若空集合也算一次 submit，就会
把现在好好锁着的 id3 解掉
——用户没让你解锁，你却解锁了（误导误锁的状态翻转）。所以"不确定 → 维持现状 + 引导"，把错误状态转移概率压到零。
比喻 4
降级链 = 各个工位的备胎方案
主厨（LLM）请假 → 切配工按标准菜单做（_rule_fallback：追踪/清除/截图仍可用，闲聊本来就不标准化——回"没听懂"）；验貌师傅（ReID）病了 → 门卫改按运动轨迹认人（features=None 纯 IoU，ID 可能短暂跳但不崩）；广播（aplay）坏了 → 改贴告示（打印降级）。
每个岗位坏了都有下位方案，全店照常营业。
比喻 5
两个看门狗 = 水位报警器
相机断流就"连续 30 次读不到"才报警（camera_stall + 暂停 1s 周期性重连，而不是 0.2s 一次无脑忙等）；LLM 卡死就"pending 持续 30.0s"解除暂停（pause_timeout）——
像水库设警戒线：到线才动作，既不误报也不放任漫坝。
比喻 6
有界队列 = 快递柜满了拒收最旧的
CommandWorker 队列 maxsize=8，put_nowait 满了丢弃最旧（E6，L220/L247-250）。LLM 风暴式连发指令也不会把内存撑爆——
柜子就这么大，新件进不来时淘汰超期旧件
，这是背压（backpressure）的最朴素形态。
🎯 一句话本质
健壮性 =
留痕
（结构化事件，可追责）+
不作恶
（不确定时零副作用）+
各退一步
（每层故障有收敛策略，绝不挂起）。三件事缺一件，系统就经不起真实环境。

09
重点与易错点
fail-closed 的判据只有一条
：该分支是否调用了 submit_effect()。任何"不确定锁谁"（id 不对齐 / VLM 无果 / 解析失败）都必须零副作用，只回引导。
绝不空 submit
：submit_effect(set()) 会清掉当前锁定——"追踪一百号"导致 id3 被误解锁，就是灾难级误导误锁。
lost 是差分不是单帧
：DeepSORT confirmed 目标 max_age=70 帧内仍存活，判定用帧间 confirmed 集合差分（prev_ids−cur_ids），单帧检测缺失不算丢。
unlock_all 只在"全解锁"时写
：clear_track 或 unlock_on_loss 全丢两条路径；follow 集合仍非空的部分丢失只写 lost。
没 follow 就没有 lost
：纯视觉 video 不追踪时日志里不出 lost 属正常——先"追踪 id3"再等出画。
完整性 = 产生的都有写
：pause_timeout/camera_stall 未出现只说明故障没触发；排查先区分"未触发"与"丢了日志"（写失败本身被吞）。
断网后闲聊不可是预期
：_rule_fallback 只覆盖追踪/清除/截图三类；若断网后连追踪都不行，查 parse_instruction 与 registry.tools。
注入后必须恢复
：llm_server、aplay、相机节点、events.jsonl 清空状态都要复位，否则污染下一实验。

10
总结与思考
本实验把系统的"下限"补齐了：events.jsonl 让状态变化可追责（五类 kind 各答一个问题），fail-closed 三条闸门（清除短路 / id 对齐 / VLM 收口）保证"不确定就零副作用"，四条降级链（规则兜底 / 纯 IoU / 播放重启 / 引导语）保证"任何异常都收敛、不挂起"，两个看门狗（camera_stall、pause_timeout）保证外部依赖卡死不冻结主循环。这是从"能跑"到"敢上线"的关键一跃。产出：E1-E3 执行表、四类注入降级记录、jsonl 完整性核对。
