02
原理通俗讲解：三级路考与体检清单
三模式入口
同一个司机，换三种"路况"
fall_app.py 的 --mode camera/image/video 经
FrameSource 统一抽象
（read/isOpened/release）走同一主循环：image=cv2.imread 单张即退、video=VideoCapture 离线、camera=惰性导入 rclpy 订阅 ROS 话题。换模式只改一个参数 ——
不是三份代码，是三种输入源插头
。
三级开发模式
先自行车场，再上路
文本→音频→摄像头是"最弱假设先跑通"：--text 只把
text_mode
置 True，输入源从 ALSA 换成 stdin 线程，
状态机与回调链一字不改
（docs/03 L5-L8）—— 所以文本模式验证过的逻辑在音频模式必然成立，音频只新增录音/识别/播放三个硬件变量，故障好定位。
五步验证手册
医生的"望闻问切"顺序
docs/03 把验收拆成 Step1 自检→Step2 文本→Step3 音频→Step4 故障排查表（按概率排五类）→Step5 摄像头，每步都有"预期日志+判定标准"。
级间有依赖
：跳过 Step1 直接 Step3，模型缺失会 mid-stream 崩溃 —— 体检没过不能跑马拉松。
证据完整性
法庭上的"三件套"
判定一次告警成功的充要条件：
截图+视频+事件日志齐，且事件覆盖 FALLING→ASK→ALERT（或 CANCELLED）
。前帧证明"跌倒前站着"、后帧证明"确实倒下了"，单帧会被"本来就躺着"骗过 —— 前后帧是最小可验证对，events.jsonl 则是可审计的推理轨迹。
🔔 人文关怀与隐私底线
验收同样克制：证据只在告警前后 5s、runs/ 全部 gitignore、testdata 视频不入库、可随时
rm -rf runs/evidence/*.avi
释放磁盘 —— 系统越"全能"，越要用数据最小化守住老人的居家隐私。

# 快速验证流程（docs/03 分步验证手册的落地命令）
cd ~/ros2_ws/src/xflz_eai_car1/app/elderly_companion
# Step 1: 环境自检（7 依赖库 + 模型文件 + 串口 + config 键）
python3 common/env_check.py --config config/fall_config.yaml
# 预期全部 [env] OK，末行 [env] 自检通过；任何 MISSING 先修再前进
# Step 2: 离线视频全链路（--text 文本模式，无需硬件）
python3 apps/fall_video_demo.py --video testdata/fall_slow_x264.mp4 --text
# stdin: 小飞小飞 →[文本] 唤醒 → 你好 →[LLM 回复] → 视频跌倒 →ASK
# stdin: 救命 →ASR 应答 x ALERT（多人也只应出现【一条】）／没事 →CANCELLED
# Step 3: 音频全链路（先清残留！aplay 占 plughw:3,0、llm_server 占 ACM0/8080）
pkill -9 aplay; pkill -f llm_server
python3 apps/fall_video_demo.py --video testdata/fall_slow_x264.mp4 --mjpeg
# 说「小飞小飞」→ 录音线程 plughw:4,0 → [diag] 录音 ~50帧/5s → 叮 → ASR/LLM/TTS
# 浏览器 http://<板端IP>:8088/fall.mjpg 确认推流
# Step 4: 实时摄像头（终端1 先起 ROS2 相机节点）
source /opt/ros/humble/setup.bash && source ~/ros2_ws/install/setup.bash
ros2 launch car1_peripherals depth_camera.launch.py
# 终端2：
python3 apps/fall_app.py --mode camera --mjpeg --save
# 预期 === 老人跌倒监护启动（mode=camera）=== → wake_seen.wait() 等唤醒
# 话题排查: ros2 topic hz /ascamera_hp60c/camera_publisher/rgb0/image
# Step 6: 证据完整性 + 资源清理
ls -la runs/evidence/
# .jpg 截图 + .avi 视频 + events.jsonl 三件套
grep -o '"to": *"[A-Z_]*"' runs/evidence/events.jsonl | sort -u
# 覆盖 FALLING/ASK/ALERT 或 CANCELLED
pkill -9 aplay; pkill -f llm_server; pkill -f fall_video_demo; pkill -f fall_app
pgrep -af
"aplay|llm_server|fall_video_demo|fall_app"
# 预期无输出
rm -rf runs/evidence/*.avi runs/evidence/*.jpg
# 可选，释放磁盘

重点与易错点
严格 Step1→5 顺序
：每级用"上一步已通过"当前提，跳步等于在未知地基上盖楼
离线也能完整验收
：无相机/麦克风时 --text 把全链路跑通，camera 只是最后换插头
单一开关切三模式
：text_mode 一个布尔位换掉整个输入源，逻辑零分叉 —— 排查先查开关
退出要温柔
：Ctrl+C 后 stop_sig.wait_grace(1.0) 给 NPU 1 秒收尾，别抢在这 1 秒里 pkill -9
现象
原因
解决
env_check 报大片 MISSING 依赖库

/home/iflytek/ros2_venv/bin/python3 运行，或先激活 venv
camera 模式无画面/输入源打开失败
ROS2 相机节点没起，或 HP60C 未连接
终端1 ros2 launch depth_camera.launch.py；ros2 topic hz 查话题

总结与思考
✅ 完成成果
六件交付
env_check 通过报告、--text 交互日志、--mjpeg 语音流程日志、camera 实时+告警记录、五步手册验收表、证据三件套与四层清理确认。
🧠 原理收获
分层验收方法论
"最弱假设先跑通"的三级开发模式为何能保证逐级不崩；证据判定为何要前后帧+事件日志三件套；单开关切模式背后的 FrameSource 抽象。
🛠 技能收获
整机排障四板斧
venv 归因（伪 MISSING）、串口/音频设备占用排查（ACM0/ plughw:3,0）、端口与内存预算体检、pgrep/pkill 分层清理与磁盘回收。
❓ 排障思路
按层下钻
先环境（env_check exit code）→ 再输入源（source.read/话题）→ 再时序（wake_seen/ask 窗口）→ 再进程残留（pgrep）—— 与五步手册同构，从下往上排查必然绕路。
🟣 思考题 1
为什么三级开发模式能保证"逐级升级不出错"？结合 docs/03 L7-L9（文本与音频走完全相同的状态机与回调链）解释文本模式验证过的逻辑为何在音频模式必然成立，再分析音频模式新增的 录音/识别/播放 三个硬件环节各自可能引入哪些新故障模式。
🟣 思考题 2
camera 模式启动后为什么要 loop.wake_seen.wait() 等硬件唤醒才开始检测（fall_app L354-L358），而 image/video 模式却自动开跑？结合 XFM 监听态不上送音频流的特性说明：若跳过等待直接检测，跌倒→ASK→应答这条链会错位在哪里？再想：一次完整告警该留"前帧+后帧"而非只存跌倒瞬间，为什么？
