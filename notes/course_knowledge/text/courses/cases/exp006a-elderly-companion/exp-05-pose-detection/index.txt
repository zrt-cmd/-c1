01
问题引入：检测框总会"缩水"的真相
第一次跑 detect_demo 的同学常惊呼："框明明画在人的身上，怎么总往左上偏一点、像没对准？" 真相是：
模型看到的图不是你拍的那张图
—— 送进 NPU 前原图被等比缩放并居中补了黑边（letterbox）。解码出的框在"补边后的空间"里，必须用 scale 和 pad 两个参数把坐标搬回原图，少一个都会整体偏移。
1
原图 → letterbox：等比缩放至 640×640 + 居中补黑边（scale、pad 两个产物）
2
NPU 推理后得到 DFL logits → softmax 加权解码出框 → NMS 去重
3
unletterbox：x_orig = (x − pad) / scale —— 少减 pad，框就整体偏一个固定量
4
姿态同理：BlazePose/RTMPose 的关键点也要 scale+pad 逆映射回原图才算数
💡 一个类比
letterbox 像
拍证件照时把人缩放后垫在一张固定尺寸的纸中央
：你在"纸面坐标"里指出的鼻子位置，想换算回"真人身高坐标"，就得先扣掉四周垫纸的宽度（pad），再除以缩小倍数（scale）。顺序错了，人就像平移了。
02
原理通俗讲解：检测与姿态的"两步舞"
检测 · YOLOv8n
一眼圈出"哪里有人"
anchor-free 单阶段：网格直接预测，每条边回归 16-bin 分布（DFL）softmax 加权成亚像素偏移；NMS（IoU 0.45）去重后只留 person（class_id=0）。nano 版约 320 万参数，INT8 量化后 30–50ms/帧，正好塞进 6TOPS NPU。
NMS 去重
像"合影只点一次名"
同一人可能被多个网格同时报框：按分数从高到低保留，凡与保留框 IoU > 0.45 的全部压掉。阈值太高（0.9）同人多框、ID 乱跳；太低（0.2）挨得近的两个人被误删一个 —— 漏检比误检更危险。
姿态 · BlazePose 33pt
"整图直出全骨架"
256×256 整图一次推理，33 点含面部/手部细节；vis < 0.5 的点不画。优势是不依赖检测框，输输出 195=39×5 交错布局。
姿态 · RTMPose 17pt
"先框人再精扫"（top-down）
单人裁剪 192×256 竖版输入，SimCC 双头输出 simcc_x(1,17,384) + simcc_y(1,17,512)，argmax ÷ 2 得像素坐标；vis = 双头峰值均值（FP32 实测有人 0.75~1.2）。躺姿裁剪稳定，是默认后端。
🔒 隐私底线
视觉层全程端侧处理：
帧只在内存流转
，除非主动 --save / --mjpeg，不落盘、不上传。testdata 为教学素材，真实部署时摄像头画面涉及老人起居隐私 —— 默认不开推流、开也要限定局域网，这是给家属的"看得见的承诺"。

06
动画讲解：letterbox → NPU → NMS → 逆映射
左侧一张竖图被缩放补边送进模型、再"拆框去重"搬回原图；右侧 SimCC 双头解码的 argmax 扫描：
YOLOv8 检测链路 · 六段
原图
竖图 384×640
letterbox
640² + pad 黑边
RKNN NPU
int8 30–50ms
box+cls 3×3 张量
DFL 16-bin logits
NMS + 反算
IoU 0.45 去重
(xyxy−pad)/scale
三个易错坐标环节：
① 补边要减
x−pad 再 ÷scale
漏 pad → 整体偏移
宽高只除 scale
② NMS 时机
score_thr 先筛候选
iou_thr 再去重
两个阈值作用不同段
③ NPU 排队
YOLO + 姿态共 NPU
帧率掉 → 关 LLM
core_mask 默认 0 AUTO
SimCC 双头解码
simcc_x (1,17,384)：34 根柱
simcc_y (1,17,512)：竖向 argmax
公式：
x = (argmax/2 − pad_w)/scale
y = (argmax/2 − pad_h)/scale
vis = 双头峰值均值
FP32: 有人 0.75~1.2
阈值默认 0.3（INT8 漂移再调）
动画 5-1｜左：原图 → letterbox 补边 → NPU 柱状激活 → NMS 双框眨闪去重 + 反算，下方三个坐标易错环节；右：SimCC 双头扫描线游走 + argmax 公式与 vis 说明

拖动等价于 CLI 的 --score-thr / yaml 的 iou_thr 预设，观察检出数与风险的跷跷板：
阈值实验台 · Threshold Bench
宽松 --score-thr 0.3

保守 --score-thr 0.7
IoU 0.9 同人多框
IoU 0.2 误删邻人
↺ 复位
// 跌倒监护是召回优先场景：漏检（人倒了没看见）代价远高于误检
当前：score_thr=0.5、iou_thr=0.45 → 实测建议区间内，检出 1 框 score≈0.837
🙋 为什么宁可"多看一眼"
误报多画一个框，顶多让姿态引擎白算一次；漏检却是
真正摔倒的老人被判定"没人"
，后面状态机、告警全部无从谈起。所以 score_thr 宜偏宽容（0.4~0.6），代价（噪声框）用 person 类过滤和 IoU 去重来兜住 —— 这是守护生命场景的取舍逻辑。

重点与易错点
六段链路每段的
形状与坐标空间
：原图 → 640² letterbox → 张量 → letterbox 空间框 → 原图框
双后端切换是
纯配置行为
：工厂 build_pose_engine 按 pose_type 创建，接口同为 process() → PoseResult
NPU 是
共享资源
：YOLO+姿态共 2 核，双模型串行排队是帧率下降主因
验证方法论：
单点 → 集成 → 调参
；单点挂是模块问题，单点过集成挂是接口/参数问题
⚠️ 常见坑
现象 → 解法
RKNN 加载失败
load_rknn failed → 核对 detect.model_path；跑 env_check 校验模型文件
need 4dims input
板端 static_shape 要求 4D NHWC → 确认 to_rgb 已补批维
检测框整体偏移
unletterbox 漏传 pad → 检查 letterbox 返回的 (r,(dw,dh)) 链路
报"未检测到人体关键点"
遮挡/模糊/vis 阈值过高 → 换图或调低 model.rtmpose.vis_threshold（默认 0.3）
RTMPose score 异常漂移
INT8 量级漂移属已知现象 → 调 vis_threshold，别急着怀疑解码
切完 blazepose 忘恢复
污染 EXP-06 判定基线 → 实验结束固定改回 rtmpose
MJPEG 404
8088 被占 → lsof -i :8088 找占用进程；start 前有端口预检
帧率低/推理堆积
双模型抢 NPU → pkill llm_server 等释放资源，关非必要服务
core None 报错
"The core mode None is not supported" → core_mask 用 0（AUTO），不是 None

🧠 原理收获
坐标空间的一致性
scale+pad 贯穿预处理与后处理；任何一步空间不一致，画面上就是"整体偏移"。
🛠 技能收获
三层验证与调参
detect/pose/fall_video 逐层单跑，再用 CLI 临时覆盖扫阈值区间。
❓ 排障思路
先看形状再看数值
报错先确认 tensor 维度（4D？195？384/512？），形状对了再查坐标与阈值。
📝 思考题 1
unletterbox 逆映射 px=(lm−pad)/scale 中 scale 与 pad 各管什么？如果只除 scale 忘了减 pad，关键点会朝哪个方向偏、偏多少像素？用一张具体尺寸的图（如宽明显小于 640）推演一遍。
📝 思考题 2
从输入方式、关键点数、躺姿稳定性、推理耗时四个维度对比 BlazePose 与 RTMPose，并解释：跌倒监护场景为什么默认选 top-down 的 RTMPose？（提示：与 crop_margin 1.5、双模型 NPU 排队一起想。）
