逆运动学固定抓取
坐标已知（手工量好、写死发布），让机械臂完成一套完整抓取：set_pick_target 只记目标不动、/arm_controller/pick 触发六阶段状态机、分步移动避开奇异、四组抓取参数决定成败——这是全课程第一次"闭环干实事"。
⭐⭐⭐ · pick/place · 状态机
01
问题引入
前五课你集齐了所有零件：协议会发、动作会放、IK 会解。现在把它们串成一件事——
抓住桌上那个立方块
。视觉还没有介入（那是 EXP-07 的事），目标坐标由你用刻度尺量出来、手工发布。别小看"写死的坐标"：从坐标到成功抓起，中间隔着目标缓存、IK 反解、分步移动、六阶段状态机、下探深度一整条链，任何一环失调都会撞桌、撞臂或空抓。

只存目标，不会让臂先动一次
；而
/arm_controller/target_pose
会
立即执行 IK 并移动
，用于预检可达性。
/arm_controller/pick

（

02
原理通俗讲解
set_pick_target 像把东西写进"待办清单"，pick 像按下"执行"键。
发话题只是记下"我要抓 (0.28, 0, 0.10)"——胳膊一动不动；直到 Trigger 服务被调用，状态机才开工。这个"先记账、后执行"的设计让你可以慢慢核对目标，而不用担心手一抖臂就飞出去。
分步移动 = 挥铁锹先对准、再下铲。
如果五个关节同时动，末端轨迹像泼水一样不可预测，还极易经过奇异位姿。car1 的
two_stage_move()
：
STAGE 1
只转底座 J1 对准目标方位，
STAGE 2
保持 J1、驱动 J2-J5 到目标姿态——先粗后精，工业机械臂的标配打法。
六阶段状态机 = 一套广播体操口令。
IDLE（立正）→ APPROACH（抬手到预抓点）→ DESCEND（下探）→ GRASP（合爪）→ LIFT（提起）→ HOLD（抱着待命）。每个口令只做一件事，做完检查（软限位、奇异）再进下一个——出错随时能停在明确的阶段上排查。
⚠️ 先说清一件事：这套"状态名"没有对外发布
讲义和上面的类比讲的是
IDLE→APPROACH→DESCEND→GRASP→LIFT→HOLD
这六个
阶段
，它帮你理解流程。但
读源码会发现
：
arm_controller.py
是
一条顺序执行的
_execute_pick()
函数
，没有状态变量、没有对外的状态话题——
/arm/grasp_state
在当前仓库里并不存在
。所以：
别去 echo 一个不存在的状态话题
；要看过程，就看节点日志里的六步顺序，或者看机械臂实际在做什么。

下探多深算"抓实"

grasp_z = 检测点z − gripper_depth

所以
正值 = 往下探
（0.01~0.03 按物深夹），

03
关联知识点
四组抓取参数
（GraspConfig，全部米/弧度）：
参数
节点默认
含义与调法
gripper_depth
0.0
arm_params.yaml 实配 −0.040
源码算的是
grasp_z = 检测点z − gripper_depth
，所以：
正值 = 往下多探
（0.01~0.03 按物深夹）；
负值 = 抬高
（指尖越过表面、跨住物侧）。节点默认 0.0 = TCP 停在检测表面；yaml 实配 −0.040 是为了让夹爪"跨"住物块。
正得太大穿桌，负得太多夹空。
pre_grasp_height
0.03
预抓取净空：
接近点 = grasp_z + pre_grasp_height
。撞桌就加大；退出也走这一点。
抬升实际也由它决定
（见下一行）
lift_height
0.05
源码未使用
声明了但从未参与计算
——
改它没有任何效果
。真实抬升 = 退回
z + pre_grasp_height
→ 再走
post_grasp_pose
。
想抬得更高，调 pre_grasp_height，不是它。
grasp_pitch
π（180°）
末端俯仰（自竖直量起，同 EXP-04 纪律）：0°=朝上 · 90°=水平 ·
180°=夹爪垂直朝下
（桌面抓取恒 180°，即四元数 {0,1,0,0}）
grasp_x_offset
0.0
抓取点 X 补偿：重力 + 齿轮间隙让臂实际停在比指令
更远
约 1.5 cm 处，
负值
把抓取点往回拉。yaml 默认 0（不再用固定值掩盖模型偏差）。
它同时作用于接近/下探/退回三个点
，所以改了不会让路径歪掉。
post_grasp_pose
[0.20, 0, 0.22, π]
抓完回到的姿态：work 位 (0.186, 0, 0.365)、pitch=90° 水平向前。源码特意
从 pre_grasp 直接跳到这里
，中间不加"垂直上抬"点——因为那个中间点在 pitch=180° 下不可达，auto-pitch 会偷偷把它掰到 ~165°，再切回 180° 时腕部翻转、末端"点头"下沉。
⚠️ 这一行最容易讲错，务必分清
抬升高度 ≠ lift_height。
源码里
lift_h = self.lift_height
确实被赋值了，但后续 6 个步骤一次都没用它。真正让物体离桌的是第 5 步"退回 pre_grasp 位置"——它把 TCP 抬回
grasp_z + pre_grasp_height
。所以物体离桌高度就是
pre_grasp_height
。这条是读码发现的讲义勘误，实测"改 lift_height 毫无变化"就是这个原因。
四位姿四元数速查
（orientation 字段）：目标垂直向下用
{x:0, y:1, z:0, w:0}
（pitch=180°）；示例放置点 (0.059, 0.074, 0.219) 用
{x:0, y:0.9826, z:0, w:0.1856}
。

/arm/grasp_state

：四参数是
节点参数
（运行时传入；没有"按物体形状分组的配置文件"——不同物块调出不同值是
调参结果
，不是预置分组）。抓之前用
预演三工具
核对：① 仿真器
http://<IP>:8000/viewer
（/viewer 后缀不能省）；② 离线 FK
pwm_to_fk_demo.py 2150 1200 2200 2275 1500
（输入五路 PWM，输出 TCP 位姿/RPY/四元数/PoseStamped）；③ 单独发 target_pose 看 5 路 PWM 确认无一路接近 500/2500 极限。

06
动画讲解：抓取六阶段 + 分步移动
IDLE →（STAGE 1 底座对准）→ APPROACH → DESCEND → GRASP → LIFT → HOLD
STAGE1 只转 J1 · STAGE2 J2~J5 到位 —— 两步分开，避开奇异
pre_grasp 0.05
10 秒一循环：记账(set_pick_target) → 两段移动 → 六阶段口令 → HOLD(等待 place)
动画 10 秒一循环：先底座对准（STAGE 1），再臂部两连杆带着夹爪到预抓点、下探（DESCEND 至物体上方 pre_grasp_height → 目标点）、合爪（GRASP，绿色爪闭合）、提起（LIFT 带物离桌）进入 HOLD。物体随 LIFT 抬起、随 place 落回——每一次状态迁移前都过一遍软限位与奇异检查。

# 预期服务：pick、place、set_grasp_target、set_gripper、go_home、go_work、emergency_stop
# 注意：/arm_controller/pick、/place 是 std_srvs/srv/Trigger（无请求字段）
# 步骤 3 · 离线预演（不动舵机）：五路 PWM → TCP 位姿交叉核对
cd ~/ros2_ws/src/xflz_eai_car1/arm/kinematics/kinematics
python3 pwm_to_tcp.py 1500 1100 2200 1850 1500
# 输出 TCP 位置 / RPY / 四元数，用于核对 set_pick_target 的目标
# 仿真预演：http://<设备IP>:8000/viewer  （/viewer 后缀不能省）
# 步骤 4a · 设置抓取目标点（只记账，臂不会动）
ros2 topic pub --once /arm_controller/set_pick_target geometry_msgs/msg/PoseStamped \
  "{header: {frame_id: 'base_link'}, pose: {position: {x: 0.28, y: 0.0, z: 0.10}, orientation: {x: 0.0, y: 1.0, z: 0.0, w: 0.0}}}"
# orientation y=1,w=0 → pitch 180° 夹爪垂直朝下
# 步骤 4b · 触发抓取（Trigger 无请求字段，命令体留空 "{}"）
ros2 service call /arm_controller/pick std_srvs/srv/Trigger "{}"
# 约 5~8 秒：开爪 → 抬到 pre_grasp_height → 下探 → 合爪 → 抬升 → 回 post_grasp_pose
# 另一条路（立即执行用于预检）：ros2 topic pub --once /arm_controller/target_pose ...（会直接动！）
# 过程怎么看：盯 arm_controller 的终端日志（六步顺序 + IK 解的 5 路角度），没有状态话题可 echo
# 步骤 5a · 设置放置目标点（仍走 set_pick_target，同时覆盖 pick_target 与 place_target）
ros2 topic pub --once /arm_controller/set_pick_target geometry_msgs/msg/PoseStamped \
  "{header: {frame_id: 'base_link'}, pose: {position: {x: 0.059, y: 0.074, z: 0.219}, orientation: {x: 0.0, y: 0.9826, z: 0.0, w: 0.1856}}}"
# 步骤 5b · 触发放置（同样 Trigger 空体）
ros2 service call /arm_controller/place std_srvs/srv/Trigger "{}"
# 步骤 5c · gripper_depth 调优对比（基线/抬高/下探三档，用 -p 覆盖节点参数）
# 重启 arm_controller 并带上新参数：
ros2 run car1_arm_controller arm_controller --ros-args -p gripper_depth:=0.02
# 对照档：-0.040（yaml 实配，抬高）/ 0.0（节点默认，停在表面）/ +0.02（往下探）
# 可调项：pre_grasp_height 0.02~0.10（撞桌加大，抬升也靠它）；grasp_pitch 保持 180 夹爪朝下
# lift_height 改了没用（源码未使用）——这一点要在报告里实测证明一次
🔍 一个隐藏的坑：publish + call 会赛跑
arm_controller
用的是
MultiThreadedExecutor
，
set_pick_target
的 topic 回调和
pick
的服务回调
跑在不同线程上
。如果你用脚本"发完 topic 立刻 call pick"，
pick 可能先看到旧目标
——源码注释里专门写了这件事，并为此提供了服务形式
/arm_controller/set_grasp_target
（
SetGraspTarget
类型，有请求字段、会等响应，所以"存完再走"是确定的）。
命令行手敲没这个问题
（两条命令之间有几秒人手的间隔），但写成脚本自动抓取时必须换服务，否则会随机抓到上一个点。
09
重点与易错点
预检纪律：
先单独发布
/arm_controller/target_pose
或用 pwm_to_fk_demo 查看 IK 解的 5 路 PWM，
确认无任何一路接近 500/2500 极限
，再调 pick。极限位附近要么软限位拒绝、要么舵机憋着力——都比"跑起来再说"便宜得多。

现象
