节点：ROS2 里的"一个岗位"
一台机器人身上有二十多个程序在同时干活——看路的、算位置的、决定往哪走的、拧电机的。ROS2 给它们各自划一个岗位、发一张工牌，让它们既能各干各的、又能互相传数据，这就是
节点
。本课把"节点到底是什么、为什么这么拆、怎么自己写一个"讲透。
难度 ⭐
2 学时
验证性
关键词 node · rclpy · 计算图

本课学完，你应该能做到

② 读懂骨架
看懂一份节点代码
拿到像

③ 独立验证

01
问题引入：一台机器人里，到底有多少个程序在干活
先别看代码，看一个更实在的问题。你让小车"到桌前把那瓶水拿过来"，它身上同时发生着这些事：
1
相机一直在拍
，每秒 30 张，不断说出"我看到了什么"。
2
雷达一直在转
，每秒 10 圈，不断说出"周围哪边有东西、多远"。
3
有个程序不停在算
："根据刚才看到的，我现在在屋里的哪个位置。"
4
还有个程序负责想
："桌在前面 3 米，先绕过椅子，走过去。"
5
最后有个程序只干一件事
：把"往前 0.3 米/秒"翻译成四个轮子该转多快，然后写进电机。
这五件事，
没有一件能等另一件慢慢做完
——相机不会为了等规划算完就停产 30 秒。它们必须同时跑、各干各的、只把结果交出去。数下来，一台能干活的机器人身上通常同时跑着
20 个以上
这样的程序。
💡 一个类比：节点就是给程序"分岗位"
把机器人想成一家餐厅：
采购
每天进货、
厨师
只管做菜、
服务员
端盘子、
收银员
只管收钱。四件事同时进行，谁也不替谁干活，只把"东西"往前传。
ROS2 干的事一模一样：把上面那五个程序各封成一个岗位，
一个岗位就是一个节点
。
· 岗位要有
工牌
（节点名），不然叫谁都不知道；
· 岗位之间要能
传东西
（话题/服务/动作，后面几课细讲）；
· 一个岗位生病了（崩溃），
只停它一个
，餐厅照常营业。
但这个类比有三处会带你走偏，先划清边界
类比只是脚手架，不能当定义用。
上面这套"岗位"说法帮你快速理解"为什么要拆"，但它有三条不成立的边界——每一条后面都会展开，这里先记住正确说法：
类比说法
✅ 事实
会踩什么坑
"一个岗位 = 一个节点 = 只干一件事"
一个节点内部可以同时发布多个话题、订阅多个话题、提供多个服务
，承担多项工作。拆分原则是
职责内聚
，不是"一事一节点"。
以为必须拆得极碎，结果几十个节点互相追数据，反而更难维护。
"每个程序配一张工牌"
可执行文件与节点不是一一绑定
：一个可执行程序里可以创建多个 Node；节点也只是进程里的一个对象。
进程 ≠ 节点。
用
ps
数进程去核对
ros2 node list
，发现数目对不上就以为出错了。
"岗位只讲分工"
分工只是一半。节点的核心能力是
通过话题 / 服务与其它节点通信，共同组成计算图
（把正在跑的节点和连线画成一张"谁连谁"的图，下面就画一张看看）。没有通信，孤立的节点毫无意义。
只记"拆"，不记"连"，后面学话题/服务时接不上。
📖 严谨定义（记住这一句，比类比更管用）
ROS2 节点是参与 ROS 计算图通信的基础单元
，依托
rcl
/
rclpy
库创建，在 DDS 发现网络里表现为一个
参与者
（Participant 侧的端点集合）。
它具备的能力是：
有名字
（可被图查询）、
有通信端点
（可发布/订阅/提供服务）、
由执行器驱动
（spin 才能干活）。三者缺一，就不算一个"活着的节点"。

一句话记住分层
上层只做判断、不碰硬件；下层只碰硬件、不做判断。判断错了改上层，硬件换了改下层——这就是"崩溃域、节奏、语言三重解耦"在真实机器人系统里的具体样子。
那为什么非要拆成这么多程序？
先别急着接受"要拆"，我们看一个
真会发生的场景
——如果硬把这三件事写进同一个程序，会怎样：
同一个故障，两种后果：相机驱动抛了一个异常
✗ 写成一个程序：一处出错，全部停下
robot_app.py（一个大进程）
相机采集 30Hz
画面抖动，抛了未捕获异常
↓ 异常没人接，整个进程直接退出
算位置
■ 一起停了
拧电机
■ 一起停了
车停在半路，还得有人去现场按重启
✓ 拆成三个进程：只停坏的那个
三个独立进程，各自跑各自的
相机进程 · 挂了 ✗
异常只在它自己内部，进程退出
定位进程 · 照常运行 ✓
继续用自己的节奏算位置
底盘进程 · 照常运行 ✓
继续响应急停 / 遥控，车不失控
相机可以单独重启，另外两个一秒都没停
（这就是"独立崩溃域"：异常不会跨进程传播）
同一个故事，还能再撞两堵墙
·
节奏
：相机 30Hz、雷达 10Hz、底盘 100Hz、导航 1Hz。四种节奏塞进一个循环，只能按最慢的走。
要么 100Hz 的电机被 1Hz 的导航拖住，要么快的抢光 CPU、把慢的饿死。
·
语言
：点云处理要 C++ 的性能，业务逻辑想用 Python 的灵活。同一个进程只能选一种，
要么牺牲性能，要么牺牲开发效率。
拆成独立进程后：崩溃不传播、节奏各自定、语言各自选 —— 这就是"拆"换来的三样东西。
图 1-2｜拆与不拆，差别不在"代码好不好看"，而在于
故障会不会扩散、节奏会不会互相拖累
。这也解释了为什么机器人软件几乎一定得多进程。
所以 ROS2 的解法就是"拆岗位"：
拆成多个独立进程，各自独立崩溃域、独立执行节奏、可选各自的语言，再用标准接口对话
。代价也很实在——你要多管一份进程、多一份通信开销，所以不是"越碎越好"，而是
按职责边界拆
（怎么拆见下节的四层）。
但"拆成独立进程"不等于"一个进程塞一个节点"
这两件事经常被混为一谈，先把它们分清楚：
进程（Process）
节点（Node）
它是什么
操作系统层面"正在运行的程序"，有自己的内存空间
ROS2 图里的一个
身份
，有名字、有通信端点
谁看得见
操作系统（
ps
、任务管理器）
ROS2（
ros2 node list
）
数量关系
不是一一对应。
一个进程里可以只放 1 个节点，也可以放 3 个。节点是进程里的对象，进程是装这些对象的屋子。
🔍 "一对一更省心"到底省在哪
本课和大部分入门教程都用
「一个程序 = 一个节点」
：写完
gas_sensor_node.py
，跑起来就是一个进程、一个节点。好处很实在——
出问题时好对付
：
· 某个节点行为不对，你可以
直接 Ctrl+C 只停它
，其它节点毫发无损；
· 反过来，如果三个节点挤在一个程序里，你想单独停掉其中一个，
只能把整块一起停
，另外两个也跟着没了；
· 排查时也直观：终端窗口里谁在刷屏，基本就能对上是哪个节点。
一句话：一对一不是规定，是"好管"。
但 ROS2
并不要求
这样。同一个程序里创建多个节点完全可以，还能省掉进程间传输开销。看这段 rclpy 示例：
import
rclpy
from
rclpy.node
import
Node
# ── 同一个 context（同一个进程、同一套 ROS 运行环境）──
ctx1 = rclpy.Context()
rclpy.init(context=ctx1)
node_a = Node(
'a'
, context=ctx1)
# 节点 a
node_b = Node(
'b'
, context=ctx1)
# 节点 b —— 与 a 同进程、同 context
# 此时 `ros2 node list` 看到 2 个节点，但系统里只多了 1 个进程
# ── 再起一个 context：仍在这一个进程里，但是彼此独立的 ROS 实例 ──
ctx2 = rclpy.Context()
rclpy.init(context=ctx2)
node_c = Node(
'c'
, context=ctx2)
# 节点 c：同进程，但属于另一套 ROS 运行环境
# 结果：3 个节点全部在同一个 Python 进程内 —— 进程 1 个，节点 3 个
⚠ 一句话记住这个区别
进程是"屋子"，节点是"屋里的人"。
一间屋子可以住一个人（最常见、最好管），也可以住三个（省房租、串门快，但一个人出事容易连累整屋）。
ROS2 把这两件事分开设计，是为了让你
按需选择
：传感器驱动这种"挂了别拖累别人"的角色，单独一间屋；同一套算法里高度耦合的几块，可以合住一间屋。

问题三：spin 到底在转什么
这是本课
最难也最关键
的一步。看代码
rclpy.spin(node)
，很容易以为它在"死循环占着不动"——恰恰相反，
它是唯一让活能干起来的东西
。
💡 把 spin 想成"老板站在大堂"
节点已经开好了四个窗口：
点餐台
（定时器）、
外卖窗口
（话题回调）、
电话
（服务请求）、
意见簿
（参数变更）。
·
有 spin
：老板站在大堂，谁来了就招呼谁——闹钟响就去做采样，有消息就去处理。活有人接。
·
没 spin
：老板回后院睡觉了。外卖小哥照样把东西送到窗口，可
东西就一直堆着，没人接
。
这就是"程序明明在跑、log 却一行没有"的真实原因——
不是坏了，是没人接活
。
① 有 spin —— 店开着，老板站在大堂
定时器到点了
话题消息到了
服务请求来了
参数被改了
executor 事件循环
有活就派给对应的回调

② 没 spin —— 老板回后院睡觉了
定时器到点了
话题消息到了
服务请求来了
参数被改了

executor 空转
💤 回调一次都没被调用
✗
消息堆在队列里
程序却已悄悄退出
同一家店、同样几个窗口——区别只在于"老板在不在大堂"。这就是
spin
的全部含义。
spin 不产生数据，它只负责"把已经到达的活派出去"。
问题四：谁在决定"先干哪个活"
到这儿有个新问题：如果同一时刻闹钟响了、消息也到了，谁先？这就引出第三个概念
Executor（执行器）
。
默认行为
单线程，排队一个个来
rclpy.spin(node)
用的是
SingleThreadedExecutor
：一次只执行一个回调，其他排队。行为可预测、不会有并发 bug，
绝大多数场景够用，也是本课用的
。
要并行时
多线程执行器
MultiThreadedExecutor(num_threads=N)
让不同回调真正并行。代价是
你的回调必须自己保证线程安全
（加锁），否则数据会乱——初学阶段先别碰。
要更细的控制
回调组 CallbackGroup
MutuallyExclusiveCallbackGroup
（同组互斥，同一时刻只跑一个）/
ReentrantCallbackGroup
（同组可重入，可并发）。用来"哪些回调允许并行、哪些必须排队"。
代码怎么写：三种执行器的启动方式
上面三张卡片说的是"是什么"，这里给出"怎么写"。
三者是层层递进的关系
：默认单线程 → 换多线程 → 用回调组精细控制。

② 多线程执行器：让不同回调真正并行
把
SingleThreadedExecutor
换成
MultiThreadedExecutor
，并指定线程数。
注意：必须自己加锁

'/cmd'

self._lock:

self._lock:

print

    node = GasSensorNode()

⚠️
多线程的代价（别急着用）
·
必须自己保证线程安全
：所有被多个回调共享的变量都要加锁，漏一个就是"偶发"的数据错乱，极难查；
·
rclpy 不是完全线程安全的
：两个回调同时调
create_publisher
/
destroy_node
这类操作可能崩；
·
调试变难
：现象不再可复现（有时对有时不对）。
结论
：先单线程跑通，确认瓶颈真的在"回调排队"上，再考虑换多线程。
③ 回调组：精细控制"哪些能并行"
多线程执行器是"整体放开"，回调组是"
按组放开
"——你要明确告诉 ROS2：这几个回调可以并行，那几个必须排队。
用法是在创建定时器/订阅时传入
callback_group
参数。

time
import
rclpy
from
rclpy.node
import
Node
from
std_msgs.msg
import
Float32
from
rclpy.callback_groups
import
(
    MutuallyExclusiveCallbackGroup,
# 同组互斥：一次只跑一个
ReentrantCallbackGroup,
# 同组可重入：可并发跑多个

rclpy.executors
import

RobotNode(Node):

__init__(self):
super
().__init__(
'robot_node'

回调组类型
同组内行为
典型用途
MutuallyExclusiveCallbackGroup
互斥
：同组同一时刻只跑一个，其余排队
操作共享硬件（如串口、GPIO）的回调，绝不能并发
ReentrantCallbackGroup
可重入
：同组可多个同时跑
纯计算、无共享状态的快回调
不传（默认）
归入节点的默认组，行为等同互斥
本课所有节点的写法
🔑
三者的关系，一句话记住
SingleThreadedExecutor
= 1 个窗口，所有活排队；
MultiThreadedExecutor
= N 个窗口，但哪些活能同时办
由回调组决定
；
回调组不换执行器就没用
——单线程下即便标了
Reentrant
，也只有一个线程在跑。
先选执行器，再用回调组微调
。
⚠ 一条铁律：回调里别阻塞
单线程下只有一个回调在跑。如果

里写了
sleep(5)
或一个慢查询，
这 5 秒内所有别的回调都停在队列里动不了
，现象就是"节点卡住了"。
回调要短
；真要干重活，丢给独立线程或另一个节点。同理：服务回调里如果调用了还要等 spin 才能完成的东西（比如同步等待），会直接死锁——这就是 EXP-07 要讲的坑。

⚠ 用词要准：这里是"组播"，不是"广播"
这两个词日常混着说没关系，但在网络层面是两回事，讲 DDS 发现时必须分清：

G. 命名规则：为什么你的话题"跑"到了别处
ROS2 的名字有三种写法，

类型
写法

相对名
★

推荐

私有名
~/state

给节点套前辍

改名不改码
第三方包适配、临时替换

07
本课总结与思考题
定位
节点 = 一个独立岗位
继承
Node
才进图；拆多节点的意义是崩溃域、节奏、语言三重解耦。
生命周期
init → 构造 → spin → 销毁
顺序不可换。只有 spin 期间节点"活着"，回调才会被执行。
发现
组播宣告 → 单播交换端点 → 匹配 → 直连
无注册中心。三项（话题名 / 类型 / QoS）任一不匹配就不通。
身份
相对名 + 命名空间
代码里不写死全局名，一套代码就能多处部署，这是多机系统的地基。
思考题
① 把
super().__init__('gas_sensor_node')
删掉，或挪到
create_publisher()
之后，程序分别会出现什么现象？请结合"注册顺序"解释原因。
② 本课里一个节点对应一个独立进程。如果机器人上有 5 个传感器，可以起 5 个进程，也可以在 1 个进程里放 5 个节点（配
MultiThreadedExecutor
）。两种方式各有什么优缺点、分别适合什么场景？
③ 如果你写了一个节点，
ros2 node list
能看到它，但把消息发出去后订阅端完全没反应。请按"spin / 节点名 / 话题名 / QoS"四个方向列出排查顺序和每一步要敲的命令。
④ 同一条
/cmd_vel
速度指令，如果改用
服务
下发会出什么问题？请从"可能有多个订阅者""每秒要发几十次""发布者不该等回执"三个角度说明它为什么天生该用话题。
⑤ 为什么说"发现层只牵线、不中转"就能避免 ROS1 那种单点故障？如果发现层自己挂了，已经在通信的两方还能继续发数据吗？
