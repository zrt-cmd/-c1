功能包与依赖管理：ROS2 的交付单元
功能包（Package）就是 ROS2 的
交付单元
：一份
package.xml
说清「我是谁、我依赖谁、怎么构建我」，colcon、rosdep 和同事全靠它干活。
本章目标：
能从零创建功能包，跑通话题闭环
——先拆两个真包看明白，再把从清单到 build / install 的编译流程走清楚，最后自己建、自己编、自己验。

01
问题引入：交付代码，怎么才不抓瞎
上一章 colcon build 你已经敲顺了，但每个源码目录里那份
package.xml
还一直没细看——今天就把它拆开。先换个角度想：
把代码交给别人，怎么才能不靠嘴解释？
各家生态早有答案了，都靠一份「说明书」：
你熟悉的生态
包里装什么
说明书（清单文件）
没有说明书，会怎样
Node.js
代码 + 启动入口
package.json
npm 不知道要装啥，
npm run xxx
直接失灵
Python
模块 + 元数据
pyproject.toml、requirements.txt
对方装不上依赖，只能回你一句"在我这能跑"
Java
类 + 资源
pom.xml（Maven）/ build.gradle（Gradle）
用了哪些库、什么版本，全靠口头相传
C / C++
头文件 + 库
CMakeLists.txt 编译规则
构建规则和依赖两头都散着——换台机器链接就失败，还不知道缺哪个库
ROS2
节点 + launch + 接口
package.xml
colcon 扫不到这个包、rosdep 不知道该补啥、
ros2 run
找不到入口
说明书上写的就是三件事：
我是谁、我依赖谁、别人该怎么构建我
。ROS2 里它格外重要——一个工作空间几十个包，机器要靠这份说明书自动排序编译、补齐依赖、登记入口，同事拿到才知道先跑什么。这一章就走三步：
看懂说明书（演示）→ 弄明白机器照着它编译时都干了啥（原理）→ 自己从零写一份、跑通（实操）。
先给个定义
功能包（Package）= 至少一个可执行/库文件 + 一份
package.xml
清单的目录。
上一章的工作空间管"一批包"，这一章的主角是"一个交付单元"
。

03
原理：从清单到 build / install
演示里两个包的差别看清了。现在回答最要紧的问题：
在根目录敲下
colcon build
之后、到
ros2 run
能跑，中间机器到底干了什么？
清单在每一步起什么作用——这条线走完，build/ 和 install/ 里为什么会多出东西，就全明白了。
先定调：两种构建类型
ament_python
纯 Python 包
setup.py + 模块目录 + entry_points 声明入口。无需编译（colcon 做安装），开发迭代最快。适合：应用逻辑、工具脚本。
ament_cmake
C++ 包
CMakeLists.txt 驱动编译，生成可执行/动态库并安装接口。适合：驱动、算法、性能敏感节点。
ament_cmake_python
混合包
C++ 为主但附带 Python 接口层（如机器人 SDK 同时给 C++ 库和 Python 绑定）。
interface 包
纯接口包
只有 .msg/.srv/.action 定义，无代码。独立成包可避免接口变更引发全量重编（EXP-09 详解）。
对比维度
ament_python
ament_cmake
构建描述
setup.py + setup.cfg
CMakeLists.txt
清单
两者都必须有 package.xml（格式 3）
编译耗时
近零（安装型）
随代码量增长
入口声明
setup.py 里
entry_points
的 console_scripts 段（建包后
cat setup.py
可见）
CMakeLists.txt 里
add_executable()
+
install()
（喏，
grep add_executable
demo_nodes_cpp 的 CMakeLists 就能找到）
典型选择
应用层/编排层
驱动/算法/接口生成
编译流程：一步清单 → 一个 build/ → 一份 install/
1
读清单（Discovery）
：colcon 递归扫 src/，只认最里层带 package.xml 的目录；没有清单的目录直接跳过。
2
按依赖排序
：清单里的 depend 连成一张图，谁被依赖谁先编。你刚 cat 过的 demo_nodes_cpp / demo_nodes_py，依赖全是 rclcpp、std_msgs 这类
系统包
，早就在环境里排好了，所以单独编译它们感觉不出先后；等哪天你自己的 my_interfaces（消息定义）被 my_app 用上，colcon 就会先编 my_interfaces 再编 my_app——注意这排的只是工作空间内的编译顺序，缺系统依赖它不管（那是 rosdep 的活）。
3
按 build_type 分流
：ament_python
不编译
——只是把执行需要的资源（.py 源文件、入口脚本、清单）安装到 install/，所以秒级完成；ament_cmake 交给 CMake 生成构建规则、g++ 执行编译，.o 中间产物堆在
build/<包名>/
。
4
装进 install/
：可执行与库放进
install/<包名>/lib/<包名>/
，清单、launch、消息定义放进
share/<包名>/
，最后汇总出一份
install/setup.bash
。
5
source 后可用
：source setup.bash 把 install/ 下的 bin、lib 注进 PATH 和 PYTHONPATH，之后
ros2 run
找得到可执行、
ros2 launch
找得到包和 launch 文件——两种启动方式都靠这一步就位。
报 Could not find / No such file？
给个真实场景
：你给包加了
<depend>image_transport</depend>
，colcon build 时 CMake 报
Could not find a package configuration file provided by "image_transport"
——不是名字写错了，是这台机器还没装这个包，而清单只是「声明了要」，
colcon 不负责下载
。这时跑：
rosdep install --from-paths src --ignore-src -r -y
（它按清单扫描，缺啥装啥）
——装完再
colcon build
，同一个包就能编过。
把依赖这条暗线画出来
package.xml
声明依赖清单
colcon Discovery
解析 workspace+系统包
rosdep / apt
缺失依赖 → 安装
链接成功
可 import / 找到接口
缺依赖分支：ModuleNotFoundError / 找不到类型定义
→ 先 rosdep install 补齐，再 colcon build 重编
依赖的生命周期：声明 → 解析 → 补装 → 链接；四个环节任一断裂都会在"链接成功"处报错。
读懂清单：字段与依赖的"生效阶段"
# 节选自真机 demo_nodes_cpp/package.xml（cat ~/ros2_ws/src/xflz_eai_car1/ros2_demos/demo_nodes_cpp/package.xml，真文件更长）
<package format="3">
  <name>demo_nodes_cpp</name>
  <version>…</version>
# 版本/维护者/license 等四件套从略
# ① 构建工具期：用什么构建我
<buildtool_depend>ament_cmake</buildtool_depend>
# ② 仅编译期（build_depend）：g++ 编代码时要用
<build_depend>rclcpp</build_depend>
  <build_depend>std_msgs</build_depend>
# ③ 仅运行期（exec_depend）：跑起来/launch 时才用
<exec_depend>launch_ros</exec_depend>
  <exec_depend>rclcpp</exec_depend>
# ④ 测试期（test_depend）：colcon test 才用
<test_depend>ament_lint_auto</test_depend>
  <export><build_type>ament_cmake</build_type></export>
</package>
# 对照 demo_nodes_py/package.xml（同样节选）——rclpy、std_msgs 挂在 exec_depend 下：
# Python 不编译，不存在"仅编译期"要装而运行期不用的依赖，所以看不到 build_depend。
# 两个文件都可以真机 cat、再用 grep build_depend 对比着核对一遍
标签
生效阶段
典型用途
depend
编译 + 运行
默认选择：消息类型、客户端库
build_depend
仅编译
头文件/生成代码需要，运行用不到
exec_depend
仅运行
launch、 rviz 配置、脚本工具
buildtool_depend
构建工具
ament_cmake / ament_python 自身
test_depend
测试
lint、pytest 套件
为什么要分阶段声明
依赖分阶段可以让 CI 只装构建依赖跑编译、部署镜像只带运行依赖——清单越精确，交付镜像越小、rosdep 解析越快。

改动 1｜文件最顶部（

import rclpy
from rclpy.node import Node
from std_msgs.msg import String
# 缺模块时：sudo apt install ros-humble-std-msgs
改动 2｜紧接着 import 下面、
def main
之前，加一个节点类
——发布者和定时器都在这里：
class HelloNode(Node):
    def __init__(self):
        super().__init__('hello_node')
        self.pub = self.create_publisher(String, 'chatter', 10)
# 发布者：话题 chatter，队列 10
self.timer = self.create_timer(1.0, self.tick)
# 每秒调一次 tick
self.n = 0

    def tick(self):
        self.n += 1
        self.pub.publish(String(data=f'Hello World: {self.n}'))
        self.get_logger().info(f'发出: Hello World: {self.n}')
改动 3｜把原来整个
def main
函数换成下面这 4 行
（print 换成初始化 + spin；spin 让进程停在这里持续发消息，不再打完就退）：
def main():
    rclpy.init()
    rclpy.spin(HelloNode())
    rclpy.shutdown()

08
本课总结与思考题
单元
Package = 代码 + 清单
package.xml 是机器可读的契约，工作空间负责组织一批包。
类型
python / cmake / 混合 / 接口
按性能与交付形态选型，接口独立成包可解耦重编。
依赖
分阶段声明
depend / build / exec / test 各管一段生命周期，越精确越干净。
工具
ros2 pkg + rosdep
pkg 自查包状，rosdep 按清单翻译并补装系统依赖。
思考题
① 一个 C++ 包用了 geometry_msgs 的消息，但只在运行期通过插件加载——依赖该写 depend 还是 exec_depend？各自代价是什么？
② 若同事机器上 rosdep install 一切正常但你报 Could not find rclcpp，可能有哪三个原因？（提示：没装 ROS2 / 没 source / 装的发行版不同）
