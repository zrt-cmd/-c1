ROS2 话题通讯原理（MQ5 气体传感器）
传感器数据像河水一样持续流动，如何让"生产数据的节点"和"使用数据的节点"互不干扰地协作？本实验以真实 MQ5 可燃气体传感器为载体，讲透 ROS2
发布/订阅
模型、
QoS 三要素
与
MQ5 对数换算
三条原理主线，并完成"DAC 采集 → 物理量换算 → Float32 发布 → 报警判定"全链路实操。
ROS2 Humble
rclpy
Publisher / Subscriber
QoS
MQ5 · ADC
实验箱 B2
目标
本课学完，你应该能做到
① 说清模型
异步发布 / 订阅
能阐述 Publisher 与 Subscriber 如何通过话题名解耦、DDS 如何自动完成发现与分发，并说明 QoS 三要素（Reliability / Durability / History Depth）如何影响通信行为。
② 掌握链路
从采样到回调
掌握
gas_sensor_node
（发布）与
gas_monitor
（订阅）从参数声明、QoS 配置到消息收发回调的完整编程链路。
③ 独立验证
自己造出证据
能独立运行 MQ5 收发节点，用
topic echo/hz/info
观察浓度、频率与类型，并用
--ros-args -p
动态改

与报警阈值。
④ 迁移应用
换传感器照样套
能把「ADC 采集 → 物理量换算 → Float32 发布」这套模型迁移到温湿度、心率血氧等其它持续数据流传感器。
本课的重点与难点
重点

和前后的关系

终端 B
启动发布端
（这个终端会被一直占住，别关）
📏
先弄清一个单位：PPM（parts per million，百万分之一）
等一下日志里会一直出现
ppm=312.91
这样的数，先说明它是什么：
PPM 是 "parts per million" 的缩写，字面意思就是"百万分之一"
，用来表示
极小的比例
。
· 用在气体浓度上：
一百万份空气里，混了多少份目标气体
。312.91 ppm ≈ 每 100 万份空气里有约 313 份可燃气体。
· 换算成百分比更直观：
312.91 ppm ≈ 0.031%
；本课默认报警阈值 500 ppm ≈ 0.05%——
浓度都很低，靠鼻子闻不出来，所以必须靠传感器
。
· 记住两个量级参照：
1000 ppm = 0.1%
；
10000 ppm = 1%
。看到 4 位数的 ppm 就说明已经是"百分之几"了。
· 为什么不用百分比：可燃气体在爆炸下限之前往往只有几百到几千 ppm，写成 0.03% 既不方便比大小，也不方便设阈值，所以行业统一用 ppm。

02
问题引入与原理：一份数据，为什么要经过"话题"
刚才那一屏数据已经跑通了。但它凭什么能跑通？先看需求——想象你在家做一个"燃气安全管家"：厨房装了
MQ5 可燃气体传感器
，一旦浓度超标要立刻做四件事：手机弹通知、客厅声光报警器响、云端留一份记录、物业大屏同步显示。传感器每秒读一次数据，这四个"想听的人"都要拿到
同一份
。
🏠
生活里到处都是这个结构
：小区广播站喊一句"三号楼停水"，不需要知道谁在家；电视台播新闻，不需要知道谁在看。共同点是——
一个人说，很多人听，而说话的人完全不必知道听众有谁
。这正是你刚才看到的：
gas_sensor_node
根本不知道
gas_monitor
和
ros2 topic echo
在听。
如果不用话题，直接让传感器程序"挨个通知"这四个人呢？这是最朴素的点对点直连，一上手就会撞到四堵墙：
① 得先认识每一个收件人
每个接收方都要写死 IP + 端口。手机换个 WiFi、云服务换个地址，程序就得改。
② 加一个人就要改一次代码
明天想再加一块"微信提醒"，传感器程序要重新改、重新编译、重新上线——加听众的成本落在说话人身上。
③ 慢的会把快的拖死
云端网络卡了 3 秒，传感器就得等它 3 秒。采样节奏被别人的网速绑架，这在安全监控里是致命的。
④ 掉线重连全自己扛
对方没开机？连接断了？排队重发还是丢弃？这些工程细节全部落到业务代码里。
① 点对点直连：4 条专线
gas_sensor

要 IP + 端口
声光报警
要 IP + 端口

要 IP + 端口
加一个听众 → 改一次发布端代码

上线就能收

话题通信的三个承诺
：①
一对多
——新订阅者随时插进来，发布端毫不知情（刚才
ros2 topic echo
就是这么插进去的）；②
异步
——发布只管把消息放到话题上就走，订阅者处理得慢也不拖累发布者；③
位置透明
——双方只需约定
话题名 + 消息类型
，谁都不需要知道对方的 IP、端口、进程号。

① common.py —— ppm 是算出来的，不是读出来的
ppm 是什么
在 01 节已经说过（parts per million，百万分之一）。这一节补的关键点是：
它不是传感器直接读出来的数字
。MQ5 是半导体气敏元件，接触可燃气体时内阻下降；电路通过分压把这个电阻变化变成电压。而"电压"和"浓度"
不是线性关系
——它的灵敏特性曲线只有在双对数坐标下才近似直线，所以必须在对数域里插值，才能把电压反推成 ppm。
① ADC 原始值
raw × scale ÷ 1000
→
② 电压 v (V)
分压电路输出
→
③ 电阻比 ratio
rs = RL·(V_REF−v)/v
→
④ ppm 浓度
10^((lg ratio−B)/M)
🔍
raw 和 scale 各管一半
：
raw
是 ADC 数出来的"格数"，12 位的一刀把量程切成 4096 格，取值 0~4095，本身不带单位；
scale
是内核驱动按"满量程毫伏 ÷ 4096"提前算好、放进 sysfs 的系数，含义是 1 格等于多少毫伏（5 V 满量程约为 1.2207）。
两者相乘得到毫伏，再 ÷1000 才是伏特
：v = raw × scale ÷ 1000。拿日志验算一遍：1404 × 1.2207 ≈ 1714 mV，正是那行的

…/in_voltage7_raw
，各板参考电压不同，以你 cat 出来的数为准。
🧭
下面四步里第④步那行长公式，是这样推出来的
：
① 手册的灵敏度特性曲线放在双对数纸上近似一条直线，横轴 lg(ppm)、纵轴 lg(ratio)，套直线方程得
lg(ratio) = M × lg(ppm) + B
；
② 把浓度反解出来：
lg(ppm) = (lg ratio − B) ÷ M
；
③ 两边同时取 10 的幂：
ppm = 10^((lg ratio − B) ÷ M)
。
代入拟合系数 B = 0.186、M = −0.362，就是④显示的那一行。整条链上 B、M 是查手册曲线拟合来的固定值，每次采样真正变的只有

timer_cb(self)
整个业务逻辑只有五步：读 → 判错 → 装消息 → 发布 → 记日志。
⑦ 发布
self.pub.publish(msg)
把消息交给话题即返回。
此刻有没有订阅者在听，它完全不关心
——这就是能"一对多、随时加入"的根本原因。
③ gas_monitor.py —— 订阅端与发布端镜面对称

回调里能做什么、不该做什么
