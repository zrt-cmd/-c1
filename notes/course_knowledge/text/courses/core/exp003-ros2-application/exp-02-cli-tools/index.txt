ROS2 常用命令工具：给系统做"体检"
一个跑起来的 ROS2 系统是
看不见的分布式进程网
。ros2 命令行是
名词域 × 动作
结构：先选名词域，再给动作——
node / topic / service / param / interface / bag 是最常用的六个命令族
，另外还有action 专管长任务，run / launch / pkg 负责启动与编排（`ros2` 还有更多名词域，用到时 `ros2 --help` 一查便知）。list / info / echo / call 是它们常用的动作。本实验以这六族为主线，教你不用读一行源码，就能回答"谁在发、谁在收、发的什么、多快"——并用 rosbag2 把现场录成可以回放的"时间机器"。

01
问题引入：程序跑起来就变成黑盒？ROS2 给了一个不一样的答案
先问一个几乎每个开发者都遇过的问题：
程序一旦跑起来，你还剩多少手段看清它在干什么？
不管写 Java、Python 还是嵌入式 C，程序运行后的"可观测手段"翻来覆去就那么几样：
手段一
看日志
最通用，也最原始。问题是：日志
是写代码的人预先决定要打印的
——他没想起来打的地方，你永远看不见。
手段二
断点调试 / 仿真器
单步执行很爽，但它要求能
停下来
。机器人正在跑、电机正在转、传感器 30Hz 在出数据——一旦停下来，现象就消失了。
手段三
抓包 / 中间件工具
能看到字节，但要
先知道去哪抓
：端口、协议、序列化格式都得事先搞清，还得会和业务字段对应上。
手段四
埋点 / 接口注入
最"正规"，代价是
要改代码、重新发布
。生产环境下往往根本不允许。
这四种手段有个共同的隐含前提：
你得先知道内部结构，才能去观察它
。于是出现一个尴尬局面——
⚠ 传统开发的"黑盒时刻"
接手一份别人写的代码、或者一个已经在跑的系统，你常常要回答三个问题：
它现在在做什么？谁在给它发数据？它发出去的东西别人收到了吗？
而传统手段的答案往往分别是：
不知道（日志没打）、不知道（代码里没写）、不知道（只能靠猜）
。
ROS2 的答案：让"内部结构"本身变成可查询的公开信息
ROS2 之所以能跳出这个困境，是因为它在架构层面做了一件别家很少做的事：
把"谁存在、谁和谁连着、连线上流什么"这件事，从程序内部搬到了系统层面，并规定所有组件都必须如实登记。
这份登记表就是上一课讲过的
计算图（Graph）

DDS 在运行时实时维护的在场名单
：每个节点一上线就自动登记自己的名字、开放了哪些话题、提供哪些服务——谁来问都一样，
不区分是"自己人"还是"路过的工具"
。
于是
ros2
这套 CLI 工具，本质上就是
一批合法的"第三方观察者"
：它以普通参与者身份加入这张图，把图里已经登记好的信息读出来给你看。

02
核心原理：ros2 的"名词域 × 动作"体系
ros2 CLI 和 git 一样是
先说对象、再说动作
的结构：
ros2 <名词域> <动作>
——先选名词域（操作什么），再给动作（怎么操作）。除六大命令族外还有 action 与执行入口一族，按职责分五组，各管计算图的一个侧面：
图拓扑
node / topic / service / action
进程、数据流、请求应答、长任务——四种图元素的 list / info / echo / call。
运行配置
param
list / get / set / dump：每个节点自带一个参数服务器，随时查改其"旋钮"。
接口定义
interface
show 查看 .msg / .srv / .action 的字段结构——通信双方的"合同原文"。
数据存档
bag
record 录制话题流 → play 回放：把现场时间冻结成可复现的数据集。
执行入口
run / launch / pkg
run 启动单个可执行文件，launch 编排一群，pkg 在已安装包里搜索。

03
异步话题 vs 同步服务——两种通信模型的对比
不要把这节理解成"两条命令的使用技巧不同"。真正的差别在
通信模型
：
topic 是异步单向的
——发布者把消息扔进话题就完事，不关心谁收、收没收到；
service 是同步一问一答的
——客户端发请求后
阻塞等待
，直到服务端回一个响应才继续往下走。
用同一个场景对比：
你想问 talker 节点"你的 use_sim_time 参数是什么"
。两种模型各写一遍，看差在哪。

Server

⚠️ 两个事实，别记混
① CLI 本身没有超时参数。
ros2 service call
只支持
-r/--rate
（重复调用频率），
没有
--timeout
。上面左栏那种"无限等"就是它真实的实现（源码见

timeout

② 写程序时，等连接和等响应这两处都要给超时。

两处都要设。
💡 还有一条官方警告：别在回调里用同步的 call()
rclpy
的
Client.call()
（同步版）内部是
event.wait()
——
永久阻塞、没有超时参数
。官方源码里明确写着
Do not call this method in a callback or a deadlock may occur
。
因为回调函数本身就跑在执行器线程里，你在回调里同步等响应，等于让执行器停下来等自己——
死锁
。回调里要用
call_async()
拿 Future，或者干脆换
call_async
+ 回调链的写法。

为什么

在没人订阅时也"成功"？——因为异步模型不定义"送达"，它只保证"投递出去"。
为什么

🛡️ 命令行也能限时：用 shell 的 timeout 包一层
上面第 ③ 步你只能
Ctrl+C
手动脱身。
但命令行并非没有办法限时
——既然
ros2 service call
自己不带超时参数，就让外层的
shell 定时器
替它掐断。这是 Linux 上处理"可能卡死的命令"的标准做法，不只用于 ROS2：
# 语法：timeout [选项] 秒数 命令...
# ③ 的改进版：最多等 3 秒，超时自动杀掉
timeout
3
ros2 service call /talker/get_parameters rcl_interfaces/srv/GetParameters
"{names: ['use_sim_time']}"
# → 3 秒后进程被终止，提示：Terminated
# → 终端立即回到提示符，不用手动 Ctrl+C
# 想知道"到底是超时了，还是命令自己失败"？用 --preserve-status 区分退出码
timeout
--preserve-status
3
ros2 service call ...
echo
$?
# 124 = 超时被杀；0 = 正常返回；其他 = 命令自身报错
# 常用选项
#   -s SIGINT   超时后发 SIGINT（相当于替你按 Ctrl+C，更温和）
#   --preserve-status  保留命令自身的退出码，便于脚本判断
#   -k 2        如果 SIGINT 不管用，2 秒后补一个 SIGKILL 强制杀
💡 三层超时，各管一段——别把它们搞混
① 命令参数层：
ros2 service call
没有超时参数，这一层是空的。
② shell 包装层：
用
timeout 3 ros2 ...
从外部掐断，适合在终端里手动排查、或写 shell 脚本时兜底。
注意它杀的是整个进程
——命令被强行终止，你拿不到"调用失败"这种结构化结果，只能靠退出码判断。
③ 代码层：
在 rclpy 里给
wait_for_service
和
spin_until_future_complete
设
timeout_sec
。这是唯一能
优雅降级
的做法——超时后程序继续执行，你可以发告警、改用备用方案、或重试。
结论：终端里排查用 ②，写进产品代码必须用 ③。
