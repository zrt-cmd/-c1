🔥 事故复盘：巡检小车的"温湿度超标报警"，为什么报了一个不存在的状态
需求很朴素：巡检测到

就上报"环境异常"。
传感器是 DHT11，
一次采样同时给出温度和湿度两个值
。既然 EXP-06 用
Float32
发 MQ5 浓度没问题，最"自然"的做法就是开两个话题各发各的：
/dht11/temperature   std_msgs/Float32   → 36.2
/dht11/humidity      std_msgs/Float32   → 82.0

不该报警
。
采样#2
33.1 ℃ / 82 %
—— 湿但温度不够。按需求
也不该报警
。
现场
湿度那条话题的第 2 条
先到
（t=2.010s），温度那条的第 2 条
排队晚了
（t=2.030s）。这 20ms 的网络抖动，在局域网上完全正常。
结果

36.2

。

采样#1   t = 1.00s
36.2 ℃   /   45 %
采样#2   t = 2.00s
33.1 ℃   /   82 %
两次都不满足
"温度>35 且 湿度>80"
② 拆成两条独立话题：各自排队、各自到达
/dht11/temperature
36.2 @1.002s   33.1 @2.030s ← 晚到
/dht11/humidity
45 @1.008s     82 @2.010s ← 先到
③ 订阅端：两个缓冲各自记"最新值"，谁先到谁先覆盖
最新温度 = 36.2 ℃
（33.1 还在路上，没进来）
最新湿度 = 82 %
（45 已被覆盖，回不去了）
④ 判定：36.2 ℃ 且 82 % → 报警 ✗ 这个"又热又湿"的状态现实中从未出现
图 9-1 · 两条各自为政的话题：订阅端"各取最新"的配对，会拼出一次现实中从未发生的环境状态
这不是代码 bug —— 变量名、循环、类型全都没错。
错的是数据结构本身
：本该原子的一份信息被拆成两条独立消息，等于把"配对的正确性"这个包袱从系统层甩给了每一个订阅者。更糟的是它
静默出错
：日志里两条数值都印得漂漂亮亮，你根本看不出它们不是同一刻的。运维跑过去一看现场一切正常，从此再没人信这条报警。
把这次事故拆开，会看到四层结构性缺陷——它们都不是"写得更仔细"能解决的：
缺陷 ①
原子性丢失
温度和湿度是同一次采样的一体两面。拆成两条消息后，它们之间只剩一个
没有机制担保的隐含假设
："差不多同时到的就是一对"。
缺陷 ②
时间对齐靠人肉
要修就得给每条消息加时间戳、在订阅端写配对缓冲。而 6~20ms 抖动在局域网上完全正常——
错误还会静默发生
。
缺陷 ③
字段一多就组合爆炸
再补上"有效位""电池电压""传感器编号"，就是 5 个话题、5 路缓冲、5 处配对逻辑。每加一个字段，发布端和订阅端都要全线改一遍。
缺陷 ④
标准库改不了
common_interfaces
是全球共享的冻结定义，你不可能往里塞一个
temperature
字段；而自己在话题上私自约定"第一条是温度、第二条是湿度"，别的节点凭什么认？
ROS2 给的答案就是
自定义接口
：用几行文本把一份数据的结构写清楚，编译成 Python / C++ 双端可用的消息类。下面先把"该打包"和"不该打包"摆在一起看：
😤 单值消息硬扛：三个话题各发各的
温度发
/temperature
、湿度发
/humidity
——
两次到达、时间对不齐
订阅方要自己做"配对"：哪条温度配哪条湿度？
加一个字段 = 全线改发布端和订阅端
就像
给你寄三张散装便签
：一张写重量、一张写收件人，丢了哪张都拼不出完整信息
😎 自定义接口：一张"标准快递面单"
一张面单固定印好格子：
重量、收件人、是否易碎
——一格不多一格不少
快递员（发布端）和收件人（订阅端）
都认这张面单
，格式永不扯皮
对应到 ROS2：
TemperatureHumidity
一条消息装下温度+湿度，天然原子性
面单格式（接口）印好后双方共守——
这就是契约

接口 = 契约
接口定义是收发双方共同遵守的
数据契约
：字段名、类型、顺序一旦编译固化，任何一端擅自改动都会破坏兼容——所以它要独立成包、版本化管理。
03
核心原理：三种接口文件结构
.msg · 零个分隔符
单段字段表
每行
类型 字段名 # 注释
。TemperatureHumidity：float32 temperature / float32 humidity——一对多持续流的数据载体。
.srv · 一个 ---
请求 | 响应
VerifyFingerprint：请求段

依赖整个实现包
