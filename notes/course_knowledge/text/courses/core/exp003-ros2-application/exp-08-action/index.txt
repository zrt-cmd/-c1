EXP-08 · 第 2 章 · 设计性 · 4 学时
动作通信：等刷卡这件事交给 Action
服务能"等到答案"，但等待期间是
黑盒
：不知道进展、不能中途放弃。动作（Action）= 服务的目标语义 + 话题的持续流——Goal 发出立即返回，服务端边执行边发 Feedback，完成后回 Result，全程可取消。本课以 RFID 读卡为载体讲透三通道与三种结局。

2
先配权限：让普通用户能碰 SPI 和 GPIO
终端 A
读卡芯片 MFRC522 走
SPI 总线
，另外还要用
两个 GPIO
做片选（CS）和复位（RST）。Linux 默认把这些设备归 root 独占，普通用户一碰就是
Permission denied
。
下面一次性放开权限，之后就不用每次都 sudo 了
——命令只需执行一次，重启后要重做（见下方提示卡）。
① SPI 设备（读卡数据通道）
# 把 SPI 设备交给 dialout 组（iflytek 已在该组内）
sudo chgrp dialout /dev/spidev1.0
# 组内成员可读写该设备（660 = 属主读写 + 组读写）
sudo chmod 660 /dev/spidev1.0
② GPIO 114（CS 片选）与 116（RST 复位）
# 先把这两个引脚"导出"到用户空间，才会出现 gpio114/116 目录
sudo sh -c 'echo 114 > /sys/class/gpio/export; echo 116 > /sys/class/gpio/export'
# 放开 114 的方向与电平文件：666 让任何用户都能读写
sudo chmod 666 /sys/class/gpio/gpio114/direction /sys/class/gpio/gpio114/value
# 同样放开 116，复位引脚也是普通用户要拉的
sudo chmod 666 /sys/class/gpio/gpio116/direction /sys/class/gpio/gpio116/value
⚠️
这三组命令分别在做什么
·
chgrp dialout
：SPI 设备的属组改成
dialout
（串口/总线设备的标准组），你的账号
iflytek
本来就在这个组里，所以改完就自动有权限。
·
chmod 660
：属主和属组可读写、其他人无权限——比
666
更安全，因为不放开给所有用户。
·
export
：Linux 的 GPIO 默认在内核里，要先"导出"给用户空间，
/sys/class/gpio/gpio114/
这样的目录才会被创建出来。
没导出就直接 chmod，会报 "No such file or directory"
。
·
chmod 666（GPIO）
：
direction
（输入/输出方向）和
value
（高低电平）必须是普通用户可写，程序才能拉片选。
🔁
重启后权限会失效
（
/dev
是内存文件系统）。三条路任选：
① 重启后重跑上面 5 条命令（最省事，本课推荐）；
② 写成 udev 规则固化（一劳永逸，适合长期开发）；
③ 临时用
sudo
跑节点——但 sudo 会清掉 ROS 环境变量，反而更麻烦。
✔ 验证：
ls -l /dev/spidev1.0
应显示
crw-rw---- 1 root dialout
；
ls -l /sys/class/gpio/gpio114/
能看到
direction
与
value
两个文件。

复现另外两种结局
终端 D
超时与取消也要亲眼各看一遍——三种结局合起来才是完整的动作语义。
命令结构和上一步完全一样
，只改了
timeout_sec
的值、以及"你怎么打断它"：
# 结局 2 · 超时 abort：故意不放卡，等 timeout_sec 秒
# 与上一步唯一区别：把 30 改成 10，这样不用干等半分钟
ros2 action send_goal /rfid_scan ros_sensor_interfaces/action/RfidScan "{timeout_sec: 10}" --feedback
# → SCANNING 持续滚动 10s → Result: success=False msg=读卡超时
# 结局 3 · 取消 canceled：上一条跑起来后按 Ctrl+C（CLI 会发 cancel）
# 这次 timeout_sec 写大一点（如 60），才有时间在中途按 Ctrl+C
# → Feedback 中断 → Result: success=False msg=已取消
✔
三种结局其实是同一个 Goal 的三种走路方式
：贴卡 → 成功（succeed）；不贴卡等满 timeout → 超时（abort）；中途 Ctrl+C → 取消（canceled）。
三者的 Result 都会回来
，区别只在
success
字段和
msg
文案——这就是"Result 必达"的含义。
02
问题引入：刷卡要等 30 秒，为什么服务不够用
你刚跑通了指纹验证（EXP-07）——那是"一问一答、几秒出结果"的典型。现在换个真实场景：
给实验室装一套 RFID 门禁考勤
。
🚪
场景：学生站在闸机前刷卡
程序发出"开始读卡"的指令后，要
等学生把卡贴上来
——可能 1 秒就刷了，也可能 30 秒都没人。这段时间里，门禁系统必须做到三件事：
①
知道还在读
（不能像卡死一样，屏幕上要显示"请刷卡…"）；
②
能中途放弃
（学生走了，管理员得能取消这次读卡，而不是干等 30 秒）；
③
有明确结局
（读到了 / 超时了 / 被取消了，三种情况都要有交代）。
这正是机器人的常态：
导航到目标点、机械臂抓取、读卡等待
——这些任务都
耗时长、进度不确定、用户可能中途改主意
。它们和"传感器每秒发一次数据"（话题）不一样，也和"问一句答一句"（服务）不一样。
🏠
生活里所有"长时间等待"都长这样
：点外卖时 APP 给你实时进度（骑手到哪了）、取消按钮（临时有事能退单）、送达确认（结果不会丢）；导航软件随时说"还剩 3 公里"，堵车了还能改路线；下载文件有进度条，能暂停取消。
共同点：任务耗时长且不确定，所以必须有进度、能放弃、有最终交代。
那用上一课的服务来做"等刷卡"行不行？直接撞上三堵墙：
📞 用服务"等刷卡"：像打了个被永久 hold 住的客服电话
客户端阻塞在
spin_until_future_complete
：
黑盒
，进展全靠猜
想放弃？
没有取消入口
，只能 Ctrl+C 杀进程——底层读卡循环还在跑
超时了只有一个失败应答，
没有"过程性"信息
可复盘
若硬轮询发多次服务调用，每次都要重新开串口、重新初始化
📦 用动作"等刷卡"：像点了一份有进度条的外卖
Goal 立即返回
：客户端发完目标继续干别的，执行在服务端后台进行
Feedback 流
：SCANNING → CARD_FOUND → …，像看骑手位置一样看进度
Cancel 随时插队
：服务端在循环里查取消请求，优雅收场
Result 必达
：成功/超时/被取消，三种结局都有明确交代
服务 = 打客服电话（等到底）
动作 = 点外卖（全程可见）
call → 阻塞中…
✗ 进度？
没有，什么也看不到
✗ 取消？
没有入口
✗ 结局？
成功 or 失败，二选一
send_goal → 立即返回
✓ 进度？
Feedback ×N 随时报
✓ 取消？
Cancel 随时插队
✓ 结局？
Result 必有，恰一次
一行等到底 · 全程不可放弃
进度可见 · 可放弃 · 结局有交代

三回调：服务端为什么拆成三个函数
服务端只有一个回调（收到请求就处理），动作服务端却拆成
三个
——因为一个长任务要回答三个问题：这个目标接不接？取消同不同意？活怎么干？
goal_callback
收不收这个目标
在 execute 之前被调：默认 ACCEPT，可拒绝（如已有任务在跑）。
cancel_callback
同不同意取消
决定 cancel 请求的 ACCEPT/REJECT；同意后 execute 内的 is_cancel_requested 才会置位。
execute_callback
干活的主体（async）
任务全程在此：循环查取消、发反馈、推进状态机、以 succeed/abort/canceled 收尾并 return result。

为什么

本课总结与思考题
模型
三通道 + 取消
Goal 立回、Feedback 流式、Result 一次性，长耗时任务的标准形态；底层是 5 条隐藏线路。
服务端
三回调 + 状态机
goal/cancel 决定准入，async execute 内查取消、发反馈、三种结局收尾。
客户端
异步回调链
goal_response → result 两环接力，feedback 中途插播，spin 贯穿始终。
硬件层
REQA → 防冲突 → UID
先 ATQA 确认在场、再取唯一卡号——顺序不可颠倒；自检先行分层排障。
