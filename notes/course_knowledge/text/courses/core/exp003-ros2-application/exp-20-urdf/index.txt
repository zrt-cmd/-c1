例 1 · 文件头与空 link — robot 是唯一根标签，空 link 就是纯坐标系
节选自 car1.urdf 开头（robot 标签横跨全文到文件末尾）
<?xml version="1.0" encoding="utf-8"?>
<robot name="car1">
<!-- 空 link：没有几何也没有质量，只当坐标系用——base_footprint 是整车"落地点" -->
<link name="base_footprint" />
<!-- 同款空 link 还有 tcp_link（末端工具点）、camera_depth_optical_frame（相机光轴系）…全文十几处 -->
</robot>
读法：
name="car1"
就是
check_urdf
第一行
robot name is: car1
的出处；空 link 不显示任何东西，只为给 TF 树提供一个原点。
例 2 · link 三重属性 — base_link 把 inertial / visual / collision 写全
节选自 car1.urdf 的 base_link（惯性矩阵共 9 个数，此处原样摘录）
<link name="base_link">
<!-- inertial：动力学读它——质量 1.97 kg + SolidWorks 算好的 3×3 惯性矩阵 -->
<inertial>
    <origin xyz="0.00119523538791205 0.00195957701632652 0.0457542650231294" rpy="0 0 0"/>
    <mass value="1.97049077979221"/>
    <inertia ixx="0.00486152635724755" ixy="2.00512337711509E-06" ixz="0.000162020407436135"
             iyy="0.00915836901735741" iyz="2.72820673876569E-06" izz="0.0130028044572217"/>
  </inertial>
<!-- visual：RViz2 读它——STL 网格 + 颜色（rgba 值域是 [0,1]，不是 0~255） -->
<visual>
    <origin xyz="0 0 0" rpy="0 0 0"/>
    <geometry><mesh filename="package://car1_description/meshes/base_link.STL"/></geometry>
    <material name=""><color rgba="1 1 1 1"/></material>
  </visual>
<!-- collision：Gazebo 碰撞检测读它，这里直接复用同一 STL（真实工程可简化成包围盒） -->
<collision>
    <origin xyz="0 0 0" rpy="0 0 0"/>
    <geometry><mesh filename="package://car1_description/meshes/base_link.STL"/></geometry>
  </collision>
</link>
读法：三块内容消费方各不相同——渲染吃 visual、碰撞吃 collision、动力学吃 inertial；
package://
是"包内相对路径"，装到哪台机器都能找到网格。三属性的完整作用表在 03 节。
例 3 · joint 之 fixed + xyz — 焊死的安装关节，xyz 就是安装位置
节选自 car1.urdf：base_footprint 与 base_link 之间的"垫高"关节
<joint name="base_joint" type="fixed">
<origin xyz="0 0 0.029" rpy="0 0 0"/>
<!-- 子 link 相对父 link：仅沿 Z 抬高 2.9 cm -->
<parent link="base_footprint"/>
  <child link="base_link"/>
</joint>
读法：
fixed
= 0 自由度、焊死不能动，只负责定安装位姿；
xyz
三个数是平移（米），遵循 REP-103（X 前 / Y 左 / Z 上）。激光雷达
laser_joint
的
xyz="0.146 0 0.087"
同理——"往前 14.6 cm、往上 8.7 cm"装雷达。
例 4 · joint 之 rpy — 旋转姿态：相机光轴系掰了两个 90°
节选自 car1.urdf：深度相机末端的光学坐标系关节
<joint name="camera_depth_optical_joint" type="fixed">
  <origin xyz="0 0.01655 0"
rpy="-1.57079633 0 -1.57079633"
/>
<!-- -π/2 ≈ -1.5708，两个 90° 把车体系掰成相机光学系约定 -->
<parent link="camera_depth_link"/>
  <child link="camera_depth_optical_frame"/>
</joint>
读法：
rpy
三个数 = 绕 X、Y、Z 的旋转弧度（roll / pitch / yaw），求值
先 rpy 旋转、再 xyz 平移
；±1.5708 就是 90°。joint 里的 origin = 子 link 相对父 link 的位姿——与 link 内 visual 下的 origin（几何体对自己的偏移）语义完全不同，详见 03 节。
例 5 · joint 之 continuous — 一直转动：四个驱动轮，转圈无尽头
节选自 car1.urdf：左前驱动轮（其余三个轮同构，仅 name/xyz 不同）
<joint name="wheel_lf_joint" type="continuous">
  <origin xyz="0.097300000000001 0.105834744636228 0.0195000000000009" rpy="0 0 0"/>
  <parent link="base_link"/>
  <child link="wheel_lf_link"/>
<axis xyz="0 1 0"/>
<!-- 轮轴沿 Y（车宽方向）——绕它一直转 -->
</joint>
读法：
continuous
=
一直转动
，无限转圈，因此
没有也不允许
<limit>
；只要给

（转轴方向）。拖滑块时轮子转不到"头"——这正是它和例 6 的分界。
例 6 · joint 之 revolute — 有限转动：机械臂关节必须写 limit
节选自 car1.urdf：机械臂第一轴（arm_joint2~5、夹爪诸关节同款写法）
<joint name="arm_joint1" type="revolute">
  <origin xyz="0.0100000000000003 0 0.0434999999999999" rpy="0 0 0"/>
  <parent link="arm_base_link"/>
  <child link="arm_link1"/>
  <axis xyz="0 0 1"/>
<!-- 绕 Z 转（肩关节回转） -->
<limit lower="-3.14" upper="3.14" effort="100" velocity="1"/>
<!-- 有限转动，四件套写全 -->
</joint>
读法：
revolute
=
有限转动
，角度被
limit
锁死在 −3.14 ~ +3.14 rad（±180°）；
effort=100
最大力矩、
velocity=1
最大角速度。拖滑块到头即停、check_urdf 缺 limit 直接报错——revolute 的 limit 是
必填项
。
例 7 · joint 之 mimic — 其他分类：左指跟着右指动
节选自 car1.urdf：左外指关节，从动于右关节
<joint name="l_joint" type="revolute">
  <origin xyz="0.01900706 0.01375021 0.0025" rpy="0 0 0"/>
  <parent link="arm_link6"/>
  <child link="l_link"/>

mimic

从动关节

r_joint

三属性为何分离
① 视觉模型数万三角形、碰撞模型要实时求交——解耦才能各自优化；② 同一个空心盒与实心铁块外观相同但惯性不同——独立声明才不撒谎；③ 纯可视化场景可只写 visual，省掉物理开销；④ Gazebo 要求三者齐全，缺 inertial 模型会乱飞、缺 collision 穿地不碰撞。

为什么是"两个发布者"分工
URDF 是
静态
结构（轮子装在哪），/joint_states 是
动态
状态（此刻转了多少度）。robot_state_publisher 把两者相乘得到每帧 TF——这正是"模型"与"状态"分离的设计哲学，同一份 URDF 可复用于全车队。
惯性矩阵——从魔法数字到物理公式
长方体 · 底盘
Ixx=m/12·(y²+z²)　Iyy=m/12·(x²+z²)　Izz=m/12·(x²+y²)
例：底盘 0.40×0.25×0.08 m、质量 3.0 kg → ixx=0.017、iyy=0.042、izz=0.053。沿某轴的惯量 = 质量对该轴分布的"转动惰性"，垂直于该轴的边长平方贡献最大。
圆柱体 · 车轮
Ixx=Iyy=m/12·(3r²+h²)　Izz=m/2·r²
轮轴沿 Y：绕轴（Y）转动惯量小、绕直径大时看 h 贡献。r=0.05、L=0.03、m=0.2 代入即可，杜绝拍脑袋的 0.01。
数学红线
矩阵必须对称正定
ixx、iyy、izz 全部 > 0，且满足三角不等式 ixx+iyy≥izz 等。非法值会让 Gazebo 求解器发散——模型原地爆炸或瞬间飞出场景。
工程护栏
初学用 1e-3 占位
只做 Rviz2 可视化时惯性可省；进 Gazebo 前若懒得算，统一写 ixx=iyy=izz=1e-3（对角等值必正定），先跑通再精算。Xacro 则用公式自动算（见本段末 Xacro 主场，实操在 04 节）。
✅ 结论：惯性按公式算，初学 1e-3 对角占位先跑通
⚠️ 风险：矩阵非正定 → Gazebo 求解发散、模型原地爆炸

注意事项与避坑清单
origin 求值顺序
：先 rpy 旋转、再 xyz 平移——顺序颠倒视觉全变；开 TF Display 查坐标轴方向。

：ixx/iyy/izz>0 且满足三角不等式，非法值 = Gazebo 爆炸；初学 1e-3 占位。
joint 类型不可混

Fixed Frame 用根 link
：必须是 URDF 中真实存在的 link 名（car1 用 base_footprint，通用写法 base_link），否则 RobotModel 拒绝渲染。

3（目标②·改语法）
删掉根标签上的
xmlns:xacro="http://ros.org/wiki/xacro"
，再运行
xacro …/car1_gazebo/urdf/car1.gazebo.xacro
，会发生什么？展开产物还能过 check_urdf 吗？
参考答案与得分点
得分点：①所有 <xacro:…> 标签不被识别——unknown macro 报错，或原样泄漏进输出 ②${} 不求值、宏不展开，产物不是合法 URDF，check_urdf 解析失败 ③修法：robot 根标签补回 xmlns 声明，且宏定义先于调用、同在 <robot> 内。（①②各 40%，③ 20%）
4（目标③·改参数）
car1.urdf 四个轮关节的 origin 把轮距 ±0.106 全部写死；要改成 ±0.13——手写四处逐一改 vs 轮关节由一个宏生成（03 节案例 A 的写法）只改一处推导式，两种做法的结果差异在哪？
参考答案与得分点
得分点：①手写方案：四处 origin 逐一手改，漏一处即左右轮距不一致，整车跑偏难查 ②宏方案：轮距收进 ${} 推导量，改一处四个轮关节全部联动 ③参数化的工程收益 = 改尺寸零遗漏、diff 屏蔽噪声。（①②各 40%，③ 20%）
5（目标④·迁移改真机）
为 B2 真机建模：轮半径实测 0.06、轮距 0.30，且要进 Gazebo 仿真——惯性还能用 1e-3 占位吗？列出必须同步改的内容。
参考答案与得分点
得分点：①不能——1e-3 只是正定占位，进 Gazebo 后惯性与真实质量分布不符，动力学失真（打滑、倾覆异常）②几何联动：wheel_radius、chassis_width（Xacro 下派生量自动更新；手写还要连 origin xyz 一起改）③惯性按圆柱/长方体公式带实测尺寸与质量重算，复核对称正定 ④验证链不变：xacro 展开 → check_urdf → RViz 目测轮距贴合。（②③各 35%，①④各 15%）
