01
引例：这束激光该画在哪
先回忆
EXP-15 rviz2 里的 Fixed Frame 下拉框、EXP-06 消息 header 里的

不同坐标系里的数据怎么对齐

1
场景
：小车顶部装了一台 2D 激光雷达，正前方 30cm 处有一个障碍物——这是

的说法（活在

）。
2
问题
：建图算法、导航算法、机械臂抓取……它们需要的都是

（

（
map
）的坐标。30cm 的雷达读数，直接丢给建图节点，地图就歪了。
3
需求
：必须有一个"翻译官"，随时回答——
"雷达系里的点 (30, 0)，换算到车体系是多少？换算到地图系又是多少？"

答案
：ROS2 的
TF2（Transform Library）
。它把机器人身上的每个部件定义为一个坐标系，维护一张

TF2 不是可有可无的辅助库——
没有 TF2，多传感器融合、SLAM、导航、机械臂抓取全部无从谈起

03
原理讲解
TF2 树：单父、无环、两条话题
建立在 EXP-06 话题与 QoS 之上——坐标系之间的"关系"也是靠两条话题发出来的。
先记住这一句：TF 的定义
TF 用一棵树，记录各个坐标系之间随时间变化的相对位姿（位置 + 朝向），不存障碍物、机器人这类空间点
——点云、栅格地图、机器人模型各在
/scan
、
/map
、
/robot_description
自己的话题里，TF 只负责"换算"：把点从一个坐标系搬到另一个坐标系该去的位置。展开读这个定义：树里直接存的是每条
父子边
，任意两个远隔坐标系的位姿是查询时沿树链式组合出来的；每条边 = 一段平移 (x,y,z) + 一段旋转四元数，
都带时间戳
——动态边（/tf）随时间更新，静态边（/tf_static）恒定但同样带时间戳。坐标系是一把把尺子，一条 TF 变换就是"
B 尺子摆在 A 尺子的什么位置、朝什么方向
"；把所有尺子的摆放关系串成一棵树，就是
TF 树
。
图 19-2 · TF2 变换树｜本图回答：机器人身上的坐标系怎么组织，为什么必须是一棵树？
✅ 结论：单父、无环、路径唯一，查询必有解
⚠️ 风险：两个节点抢同一 child 配不同 parent → 报冲突
🔍 验证：02 节步骤 ② · 04 节第 4 步树形核对要点
TF2 把机器人身上所有坐标系组织成一棵树：
每个坐标系最多一个父坐标系，不能成环
。典型结构：
map                              ← 世界原点（SLAM 维护）
└── odom                         ← 里程计原点（会漂移）
      └── base_link               ← 车体中心
           ├── laser_frame        ← 雷达（安装位置 = 静态变换）
           ├── camera_link        ← 相机
           └── arm_base
                └── gripper_link  ← 夹爪
意思很直白：
laser_frame 的父是 base_link，base_link 的父是 odom，odom 的父是 map
。任何两个坐标系之间只有一条路——所以查变换永远有唯一解。
ROOT · 世界
map
全局地图原点，由 SLAM / 定位节点维护，漂移会被不断修正。
里程计系
odom
轮式里程计原点，短时间平滑但会长期漂移。
车体系
base_link
机器人本体中心，一切传感器都最终挂到它身上。
传感器系
laser_frame / camera_link
雷达、相机各自的测量原点，安装位置即静态变换。
✦ 失败模式：为什么禁止成环？
一旦 A 是 B 的父、B 又是 A 的父，沿父指针
向上爬就永远爬不到头
，查询陷入死循环。所以 TF2 强制一棵树——树形结构正是查询能在有限步内结束的前提。两个节点抢同一个 child 的 parent 时，TF2 会直接报错警告。

注意它不是参数的机制

凡是"后加入的节点也必须拿到"的数据，就该给它 Transient Local。
两类角色
，分工和话题的 pub/sub 一模一样——一个广播，一个监听：
角色 1 · 广播器 Broadcaster
告诉所有人："父→子"的变换现在是多少
谁来发：
里程计节点发 odom→base_link；robot_state_publisher 读 URDF 发传感器位姿；标定好相机外参后发 base_link→camera_link。
两种：
静态
（装好不变）用 StaticTransformBroadcaster，
只发一次
；
动态
（一直在变）用 TransformBroadcaster，
持续重发
。
角色 2 · 监听器 Listener
订阅 TF，随时被问"A 到 B 的变换是多少"
谁来听：
SLAM 把点云转到 map；Nav2 判断目标点相对车体多远；视觉识别到物体后转到 base_link 做抓取。
查询要给三样：
目标坐标系、源坐标系、时间戳——TF 带时间缓存，可以回查过去几秒（查询入口见下一主场）。
✦ 为什么这么设计？三句话
①
解耦
：雷达节点只管发雷达系的数据，装在哪、map 长什么样它不关心——坐标系关系全由 TF 统一维护，谁都能查；
②
自动链式
：你只发布"自己负责的那一条边"，连乘合成、跨树查询交给 tf2，永远不用手写 4×4 矩阵；
③
带时间缓存
：传感器数据有延迟，查询时可以"回查"几秒内的历史变换，用
数据自己的时间戳
去对齐，点云才不会飘。

接上一主场的"监听者"——要问"雷达系里的点 (0.3, 0)，在 map 里是哪"，tf2 只干两件事：
先向上爬，再向下拼

，收集沿途每一段变换；

也向上爬，找到两条路第一次相遇的
共同祖先
（汇合点）；
从汇合点
按下回程
，该取逆的取逆、该连乘的连乘，拼出 A→B 的总变换。

怎么设置（可照抄入口 · 查询两行起手式）
先挂监听再查询：
self.buffer = Buffer()
→
self.listener = TransformListener(self.buffer, self)
→
self.buffer.lookup_transform('map', 'laser_frame', rclpy.time.Time(), timeout=rclpy.duration.Duration(seconds=1.0))
。
三个参数的含义
：目标系（转到哪）、源系（数据原来在哪）、时刻（
Time()
= 最新；传具体时刻则用缓存历史插值）——04 节代码 B 是它的完整形态。
静态边
base_link → laser_frame
出厂安装决定，一次发布，靠 /tf_static 的 Transient Local 让后加入节点也能读到。
动态边
map → odom → base_link
定位/里程计 10-100Hz 持续刷新，新订阅者只取最新一条（KeepLast）。
合成责任
谁都不用管全树
每个节点只发布自己那一段边，跨 4 层的变换交给 TF2 自动连乘。
时效对齐
时间戳插值
查询带时间戳 t 时，对两条动态边在 t 附近做插值/外推，保证"同一时刻"的几何一致。
✅ 结论：每节点只发布自己那条边，跨树查询交给 TF2
⚠️ 风险：多源数据不传同一时间戳 → 插值错位、点云漂移
🔍 验证：04 节第 5 步 tf2_echo 持续刷新的数值（拖滑块即变）

半角公式（本实验只需 yaw）
：机器人在地面打转，本质是绕 Z 轴转
yaw
角，四元数退化为两个非零分量：
# 绕 Z 轴旋转 yaw：四元数只有 z、w 两个分量非零
z = sin(yaw / 2)
w = cos(yaw / 2)
# x = y = 0
# yaw = 90°  ⇒  z = sin45° = 0.7071,  w = cos45° = 0.7071
# yaw = 180° ⇒  z = sin90° = 1.0,     w = cos90° = 0.0
# 反解：yaw = 2·atan2(z, w)   ← 看代码时反过来算角度就用它
💡 记忆锚点
"
半角
"是关键：四元数存的是 yaw/
2

atan2(z, w) * 2
就是在从四元数反求偏航角。

命令一：读出 /tf_static 里的全部静态边
终端 B

✔ 条目能和 URDF 里每条 fixed 关节逐一对账；launch 后一次性到齐、之后不再刷新（静态 = 只发一次）。

注意事项与验收
注意事项（七条红线）
类别
说明
禁环防空转
TF2 是有根树，
严禁成环
；同一 child_frame 被两个节点配不同 parent 发布时会报错警告（"frame conflicts"）。
frame 名字一个字符都不能差
laser_link
写成
laser_Link
（大小写）或多一个空格 → 报
Frame does not exist
。排查时先
ros2 run tf2_ros tf2_monitor
或 view_frames 对名字。
别把父子顺序写反
lookup_transform(target, source)
是"把 source 的数据转到 target"——写反等于求逆变换，坐标直接飞出地图。记法：
目标在前，源在后
（数据从后往前流）。
时间戳一致
动态查询默认按
最新时刻
对齐；多源数据融合时显式传时间戳，否则插值错位会出现"点在地图上漂"。
静态用对 Broadcaster
静态变换务必用
StaticTransformBroadcaster
（/tf_static + latch）。用普通 TransformBroadcaster 循环重发静态值 → 占带宽、后加入节点仍可能漏。
四元数单位化
rotation 必须满足 x²+y²+z²+w²=1；(0,0,0,1) 表示零旋转；自算角度后记得转四元数再塞进消息。
牢记报错就在现场

是否一致。

06
本课总结与验证题
成果
跑通 launch 案例的五步闭环
一条 display.launch.py 拉起三节点；URDF 写边、robot_state_publisher 发边，树（frames.pdf）、单边（tf2_echo）、画面（RViz）三重验证全通过。
原理
树 + 连乘 + 缓冲
TF2 = 有根树（无环保证查询终止）+ 边的连乘合成 + 带时间戳的 Buffer 缓冲插值。
QoS
动态 KeepLast vs 静态 Transient Local
/tf 要"最新"（KeepLast）、/tf_static 要"后到也有"（Transient Local）——同一套 Durability 开关的两种业务化用法，与 EXP-06 的 QoS 三要素一脉相承。
迁移
四元数反解 yaw
2·atan2(z, w) 是读码必备；机械臂姿态、相机位姿都是同一套四元数。
验证题（改动型 · 每题先自己作答，再展开核对）
1（目标①②·改 QoS）
把发布静态变换的代码从
StaticTransformBroadcaster
换成普通
TransformBroadcaster
（默认 KeepLast + Volatile），仍每 100ms 重发一次。之后启动的
view_frames
与新节点还能拿到这条边吗？从 Durability 语义说明。
参考答案与得分点
得分点：①Volatile 不为迟到者保留历史，新订阅者只能等下一条到达——在"只发一次"的静态场景里就是彻底丢失 ②换回 StaticTransformBroadcaster（/tf_static + Transient Local）才对 ③动态边之所以可以 Volatile，是因为它持续重发。（①③各 40%，② 20%）

4（目标①·改结构）
如果里程计节点把
odom→base_link
这条一直变化的边发到
/tf_static
上，车开动后 TF 树会发生什么？从 QoS 与更新策略两方面解释。
参考答案与得分点
得分点：①/tf_static 是 latched 的最后一条快照，车开动后新值发不上来（或只在最后一次重发时被覆盖）②树里这条边"冻住"，map/odom 与 base_link 的关系不再更新，定位在 RViz 里纹丝不动 ③正确做法：动态边走 /tf 持续重发 + KeepLast，静态边才走 /tf_static。（①②各 40%，③ 20%）
