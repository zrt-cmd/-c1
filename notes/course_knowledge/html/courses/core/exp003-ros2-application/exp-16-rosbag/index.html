rosbag2 数据录制与回放：把现场带回实验室

最难的 bug 往往只在客户现场出现一次：车到了特定角落才定位漂移，回来怎么调都正常。rosbag2 把整条话题的时间序列原样录进文件，回到实验室"时光倒流"反复重放——本课讲清 SQLite 存储与 CDR 序列化的原理，掌握 record/play 参数族与带时钟的离线回放流。

01问题引入：只会来一次的现场故障

先回忆EXP-06 的话题数据流过了就没了、EXP-11 的时间戳与 use_sim_time——本章解决的问题是：数据流过就消失，怎么"录下来、倒回去"反复研究。现场故障只发生一次，但录好的包可以回放一万次。
1
偶发

仓库小车在 3 号货架角落必现定位跳变，开回调试室就永远复现不了

2
代价

一次现场复查：出差 + 布置笔记本 + 人守着——每次以"小时"计费

3
本质

故障 = 某时刻某组消息的特定内容，现场没录下来就永久丢失

4
正解

ros2 bag record 现场录 5 分钟 → 带回工位 ros2 bag play 想放几遍放几遍

定义 rosbag2 是 ROS2 的数据记录与回放框架：record 把指定话题的每条消息连同时间戳写进文件；play 按原时序（或加速/减速）重新发布出来——订阅节点"感觉不到"这些消息是历史还是现场。调试成本从"去现场"变成"回工位"，硬件依赖型调试工作量可压缩 80% → 20%。
本实验的示例数据源：talker / listener 本课全程用 ROS2 官方演示包 demo_nodes_cpp 的 talker（发布 /chatter） 与 listener（订阅 /chatter） 作为"现场"与"回放验证端"：不依赖任何硬件就能走通录→查→放全流程，talker 标称 1Hz 让"频率对不对得上"一眼可判（实测约 1.03Hz，属正常抖动）。
理解机制后，再把数据源换成 B2 实验箱的 /scan、/odom、相机话题——命令完全一样。
# 两个终端各起一个，保持运行
ros2 run demo_nodes_cpp talker  ·  ros2 run demo_nodes_cpp listener
🔎 是什么

ROS2 官方的数据记录与回放框架：一个 bag = 一个目录（*.db3 SQLite 库 + metadata.yaml 清单），里面装着话题消息的时间序列 + CDR 原始字节。

❓ 为什么

因为现场故障只发生一次，而数据流"流过即消失"。没录下来就永久丢失，只能出差重跑；录下来就能在工位上回放一万次。调试成本从"去现场"变成"回工位"。

🛠 怎么用

三条命令走完全流程：ros2 bag record 录 → ros2 bag info 体检 → ros2 bag play 回放。要跟 TF/定时器联调时再加 --clock 与 use_sim_time:=true。

02先看现象：录一次，历史就留住了

2 分钟 0→1先不讲原理——把 talker / listener 起起来、录一段、再回放，你会亲眼看到"已经流走的历史"按原节奏重新发布，订阅端毫无察觉。
1
造现场

开两个终端分别起发布端与订阅端——listener 每秒打印一条 world，就说明"现场"活着：

# 终端 A · 发布端
ros2 run demo_nodes_cpp talker

# 终端 B · 订阅端
ros2 run demo_nodes_cpp listener
2
开录

第三个终端开录，保持运行约 15 秒再按 Ctrl+C（SIGINT）优雅停止——这一停决定了 metadata.yaml 会不会被写出来：

# 终端 C
ros2 bag record -a -o exp16_full
3
体检

不用回放，info 毫秒级回答"录了多久、有没有这个话题"：预期 Duration 约 13.5s、/chatter Count 约 14 条（14 / 13.55 ≈ 1.03Hz，对得上 talker 的 1Hz）：

ros2 bag info exp16_full
4
断源

回放前先把真源掐掉：在终端 A 对 talker 按 Ctrl+C（SIGINT）——现场彻底静默、listener 不再收到任何东西，接下来 listener 打印的每一条都必然来自 bag，新旧消息不会混流。（这步是按键动作，没有可复制的命令）

5
复活

回到终端 C 回放，历史按原节奏重新发布，listener 会像什么都没发生过一样继续逐条打印：

ros2 bag play exp16_full
6
变速

同一份数据二倍速播放——只改发布节奏，不改消息内容，打印速度翻倍即证明时序被完整记录：

ros2 bag play exp16_full -r 2.0
此刻你已经验证的两件事 ① 持久化：消息以 CDR 字节写进 .db3，断源后依然存在（info 能数出条数与时间跨度）；
② 原时序重建：play 按时间戳重新发布，-r 改变的是发布节奏而非数据内容——这两点就是后面 03 原理的全部出发点。

03原理讲解

一个 .db3 文件里到底有什么

先看外层：目录树 别急着钻进 .db3——先看它待在哪。一个 bag = 一个目录，录完 exp16_full 后里面就两个文件，谁是本体、谁是清单一眼分清：
ls -l exp16_full/
# 目录树（先看结构，再看字节数） exp16_full/ # bag 目录本身，这就是"一个 bag" ├── exp16_full_0.db3 36864 B # 本体：SQLite3 数据库（两张表在里面） └── metadata.yaml 3297 B # 清单：记录时长/条数/指向哪个 _0.db3
$ ls -l exp16_full/ total 40 -rw-r--r-- 1 iflytek iflytek 36864 Oct 29 14:10 exp16_full_0.db3 -rw-rw-r-- 1 iflytek iflytek 3297 Oct 29 14:10 metadata.yaml # ⚠ 注意文件名带 _0 分片号，加了 -d 才会出现 _1 _2 ...；查总数要对着目录，别只查单个 _0.db3
读树的三个要点 ① 目录就是 bag——拷贝/上传/发给别人，拷的是整个 exp16_full/，只发 .db3 会丢清单；
② 两个文件缺一不可——yaml 管"找得到"（info/play 先读它），db3 管"内容在"（消息字节全在这）；
③ 树只到文件这一层——.db3 里面才是本课真正要拆的两张表，接着往下看图 16-1。

存储结构
SQLite3 双表 + 元数据

一个 bag = 目录：*.db3 数据库 + metadata.yaml 清单。库里两张表——topics（话题ID→名称/类型/QoS）与 messages（时间戳+话题ID+CDR 字节流）。YAML 记录时长/条数/相对路径，删除它 bag 就"失忆"。

为什么选 SQLite
四条硬理由

① 自带索引→任意时间点随机访问；② 事务机制→写到一半断电最多损坏最后一笔；③ SQL 直接聚合分析（频率=Count/Duration）；④ 单文件好搬运好上传。

序列化
CDR：和 DDS 同一种字节

存的就是 DDS 线上传输的 CDR 序列化结果——回放时零转换直接发出，语义 100% 保真。这也是为什么 rosbag2 不需要每种消息写专用适配器：只要类型支持接口定义，就能录能放。

两个缓冲别混
max-cache ≠ max-size

--max-bag-size：单位是字节，单文件写满自动切分新 .db3（控制磁盘文件粒度）；--max-cache-size：内存写盘缓冲（调小→高频消息排队溢出丢数据，默认 100MB 够用，4K 相机再加大）。

决策点选择理由
录全部还是选话题选话题（生产标准）1080p 彩色原图（image_raw，8UC3 未压缩）30Hz 单话题约 178MB/s，-a 全录磁盘秒爆还混入系统噪音
要不要压缩看 CPU 余量省盘 30-60%，代价 RK3576 级 SoC 约 +10-20% CPU；必须 mode + format 双参数同写
哪些话题必录感知+定位+控制闭环scan/imu/camera + odom/tf + cmd_vel + 关节——修复故障的最小证据链
QoS录时声明，放时匹配best_effort 的传感器话题用 --qos-profile-overrides-path 传入 YAML 重声明，否则回放对不上（见坑表）
要点 bag 的时间戳有双来源：默认情况下，bag 里的排序时间是 record 节点本地接收时刻（加 --use-sim-time 录包则改用消息收到的 /clock 值）；消息内部 header.stamp 是传感器采集时刻。两者在传输延迟大时会差异明显——录包只录"开始之后"，录得太短（< 1~2 秒）可能直接 0 字节，先看 metadata 再走人。
🔎 是什么

一个 bag 目录里是两张 SQLite 表 + 一份 YAML：topics（id→名称/类型/offered_qos_profiles）与 messages（时间戳 + topic_id + CDR 字节流）。QoS 就存在 topics 表里，这正是"元数据一次成形、后续秒查"的底气。

❓ 为什么

因为 SQLite 同时给了索引随机访问、事务抗断电、SQL 聚合、单文件易搬运四样——换任何别的存储格式都要自己重造一遍这些能力。

🛠 怎么用

平时不用直接开库——ros2 bag info 读 metadata 就够了；要自己算统计时用 python3 -c "import sqlite3; ..."（本机没有 sqlite3 命令行）。

record 与 play 的参数族

record · 范围
-a 全量 vs 点名

-a 录所有（含系统话题，磁盘杀手）；ros2 bag record /t1 /t2 点名录——生产标准永远是点名 + -e 正则（如 -e "scan|odom"）圈最小证据集。

record · 范围与切片
-e 正则 · --max-bag-duration · -o 命名

-e "chatter|odom" 正则圈话题；-d 3 是 --max-bag-duration——每 3 秒切一个分片（录 12 秒约出 4 片 _0/_1/_2/_3），不是延迟开录！-o exp16_full 指定输出目录名（默认按时间戳，难找）。限时录制无专用参数，用系统 timeout 15 ros2 bag ...。

record · 保命参数
--max-bag-size / --max-cache-size

前者控制单文件切分，单位是字节——写 2147483648 才是 2GB/文件；后者控制内存缓冲（默认 100MB，写不及会丢消息）。注意：小数据量下即使写了也不会切分，静默无提示（见 06·续 节实测）。

record · 压缩
mode + format 必须成对

--compression-mode message（逐条，兼容性最好）/ file（整库，省空间最多），必须配 --compression-format zstd。RK3576 级 SoC 约 +10-20% CPU——录摄像头时先跑 top 看余量，CPU 打满丢的是更多数据。

play · 节奏
-r 倍速 · --loop · --start-offset

-r 2.0 二倍速快进、-r 0.5 慢放细看——只改发布节奏，不动消息内时间戳；--loop 循环（tf_static 必备）；--start-offset 5 从第 5 秒起播。

play · 时钟与话题
--clock · --topics（无 -t）· -q

--clock 以 约 40Hz 再生 /clock（use_sim_time 节点必开）；选话题必须写全 --topics /chatter（play 没有 -t 短选项，只有 record 才有）；暂停/单步（空格/→）逐帧审；-q 静默重复警告。

参数易混对第一个第二个
切分 vs 缓冲--max-bag-size：字节单位，文件写满换新 .db3--max-cache-size：内存攒批写盘，小了丢消息
-d vs --start-paused-d 3：每 3 秒切一片（分片时长）--start-paused：启动后暂停，空格才开始
调速 vs 改时间-r 2.0：消息来得快一倍消息内部 stamp 原封不动（仿真时间另走 --clock）
Ctrl+C vs kill -9Ctrl+C（SIGINT）才是优雅停止：recorder 捕获后刷完缓存、写 metadata.yaml、关库kill -9（SIGKILL）不可被捕获，内核直接杀进程：缓存丢、metadata.yaml 不写、SQLite 可能半写损坏。万不得已才用，且事后先 ros2 bag reindex
-a vs 点名/-e-a：省事，磁盘和噪声都爆点名+正则：生产标准，最小证据链
--compression-mode vs -formatmode 单独写会被静默忽略（metadata 里为空串）必须同时给 --compression-format zstd
🔎 是什么

两族参数的分工：record 管"录什么、录多大、压不压"（范围 + 体积 + 编码）；play 管"怎么放"（节奏 + 时间 + 话题选择）。

❓ 为什么

因为录制与回放面对的是两套不同的约束：录制时受磁盘与 CPU 限制（要控制体积），回放时受下游算法与渲染限制（要控制节奏与时间基准）。所以参数族必然分成两队。

🛠 怎么用

录：timeout N ros2 bag record 点名 -o 名字 --max-bag-size 字节。
放：ros2 bag play 名字 -r 倍速 --topics 话题 --clock。记住三条硬规则：限时用 timeout、play 选话题用 --topics、压缩必须双参数。

$ cat exp16_full/metadata.yaml

rosbag2_bagfile_information:
  version: 5                        # 清单格式版本，rosbag2 升级会变（跨版本读包先看它）
  storage_identifier: sqlite3       # 存储后端 → 决定你能不能用 SQL/python 直接查库
  relative_file_paths:              # 消息本体在哪：指向 _0.db3（分片多了这里就多行）
    - exp16_full_0.db3
  duration:
    nanoseconds: 13554570568        # 录制时长（纳秒）= 13.55s，注意不是 15s
  starting_time:
    nanoseconds_since_epoch: 1760000000000000000   # 起录绝对时刻（Unix 纪元纳秒），多包对齐用
  message_count: 54                 # 全包总条数，应 = 各话题之和：14+40+0+0
  topics_with_message_count:        # 每话题一段明细，info 的 Topic 表就是它
    - topic_metadata:
        name: /chatter              # 话题名（回放时按它重建发布端）
        type: std_msgs/msg/String   # 消息类型（类型不对 play 会拒收）
        serialization_format: cdr   # 序列化格式，与 DDS 线上字节同源
      offered_qos_profiles: "- reliability: 1 ..."   # 录时声明的 QoS，回放靠它对齐订阅端
      message_count: 14             # /chatter 条数 → info 的 Count、心算频率的分子
    - topic_metadata:
        name: /rosout
        type: rcl_interfaces/msg/Log
        serialization_format: cdr
      message_count: 40
    ...                              # 省略 Count=0 的 /parameter_events、/events/write_split

    
✔ 这块 YAML 的读法："−" 开头的是列表项（每个话题一段），缩进 2 格是键值对。上半部分回答"这个包整体是什么"（版本/后端/文件/时长/总数），下半部分 topics_with_message_count 回答"里面有哪些话题、各多少条"——ros2 bag info 打印的每个数字，都能在这里指出出处。

    

      
字段（本例值）是什么用来干什么 / 不懂会怎样

      
version: 5清单格式版本号新版 rosbag2 读旧包、字段增减时的兼容依据；报"不支持的 bag 格式"先看它

      
storage_identifier: sqlite3存储后端（不是文件后缀决定的）声明是 SQLite → 可用 python3 -c "import sqlite3; ..." 直查；换成 mcap 就得换工具

      
relative_file_paths本体文件的相对路径（分片多则多行）yaml 靠它找到 .db3——所以两者必须同目录：只拷 .db3 或移动不同步，info/play 就找不到

      
duration.nanoseconds: 13554570568真实录制时长 = 13.55s（纳秒）是 info 的 Duration，也是算频率的分母；比"按了约 15 秒"短，因为开录/停止有开销

      
starting_time.nanoseconds_since_epoch起录的绝对时刻（Unix 纪元纳秒）多段 bag 拼接、和其他数据源（日志/里程计）对齐时间轴时的基准

      
message_count: 54全包总条数应等于各话题之和（14+40+0+0=54）；对不上说明清单与库不同步，先 ros2 bag reindex

      
name / type / serialization_format话题名、消息类型、序列化格式play 据此重建发布端；类型或格式不匹配的订阅端收不到（自定义消息尤其要先 ros2 interface show 核对）

      
offered_qos_profiles录这个话题时声明的 QoS（reliability/durability…）QoS 就存在这里：best_effort 传感器消息回放时按它对齐，否则"包在、却收不到"（见坑表 --qos-profile-overrides-path）

      
message_count: 14（每话题）该话题条数info 的 Count、频率心算的分子：14 / 13.55 ≈ 1.03Hz ✓

    

    
三处心算，30 秒自检这个包
    ① 加法：总 54 = 各话题 14+40+0+0，对得上 → 清单和 .db3 是同步的；

    ② 换算：13554570568 ns ÷ 10⁹ = 13.55s（纳秒 → 秒），和 info 的 Duration 一致；

    ③ 频率：14 ÷ 13.55 ≈ 1.03Hz，对得上 talker 标称 1Hz → 数据完整没丢帧。

    三处都对，才轮到 play 回放；任何一处对不上，先回查录制过程（是否 Ctrl+C、有没有 kill -9）。

反直觉现象真相

      
/parameter_events 常常是 0节点启动后不再发参数事件，所以录到 0 条（不是 3 条）——正常

      
/rosout 比业务话题还多每个节点的每条日志算一条，talker + listener 叠加约 40 条——正常

      
Duration 不是 15s 而是 13.5stimeout 15 是命令墙钟上限，节点启动约花 1.5s这段时间还没开录。心算频率要用真实 Duration，别拿 15 去凑（否则得 0.93Hz 会误判掉数据）

    Duration = 0 或 Count 明显偏少 → 废包，重录。一句 ros2 bag info 十秒钟，省掉的是明天重跑现场的一整天。

    ros2 topic delay 依赖消息里的 header.stamp 与当前时钟对比。std_msgs/msg/String（/chatter）没有 header 字段，直接跑会报 msg does not have header。

    正确做法：换用带 header 的传感器话题验证——ros2 topic delay /scan、/odom、/imu。

    数据不够怎么办：本实验 /chatter 是 String 类型，rviz 展示效果有限。若 B2 实验箱深度相机可用，录 ros2 bag record /camera/color/image_raw -o exp16_camera_test → play --clock + rviz2 --ros-args -p use_sim_time:=true → 加 Image Display（Topic 填 /camera/color/image_raw），即可重现相机画面。

  

  

    
坑症状解法

    
回放后 listener 收不到订阅方全程静默QoS 不匹配：play 默认以记录时的 QoS 发布（实测 /chatter = RELIABLE + VOLATILE），用 --qos-profile-overrides-path 传 YAML 重声明

    
tf_static 只发一次节点 late-join 错过静态变换play 加 --loop（每圈重播一次 /tf_static），或用 --qos-profile-overrides-path 把 durability 改为 transient_local

    
/clock 没开或没认Time 面板为 0 / 不动、STAMP 错位play --clock + 节点/rviz use_sim_time:=true，两个开关缺一不可

    
topic delay 报 no headermsg does not have header换带 header 的话题验证（/scan、/odom）；/chatter 是 String 类型，没有 header

    
回放太快渲染卡顿rviz 跟不上、掉帧-r 0.5 降速给渲染留时间，或用 --topics 只放特定传感器话题

    
--clock 时间跳变警告TF2 Buffer 报 WARN回放结束/跳回开头时 /clock 大幅跳变，属正常；用 --start-offset 从中间起播可避免

    
话题名大小写--topics 指定了却"没这话题"与 list 输出逐字比对，ROS2 话题名大小写敏感（/Chatter ≠ /chatter）

    
丢消息高频话题 Count 低于预期调大 --max-cache-size（默认100MB）、关无关话题、查 CPU 打满

时间戳去哪了
  bag 唯一保证的是相对时序：回放把录制时的间隔原样（按 -r 缩放）还原，但绝对时刻可以被 --clock 重映射。因此判断"延迟多少毫秒"要用消息 header.stamp 相减，而不是看 bag 播放墙钟——header 才是传感器时间的原始证据。

  注意：也正因为这条原理，验证时钟的 ros2 topic delay 只能对带 header 的话题用——/chatter（std_msgs/msg/String）没有 header，会直接报 msg does not have header。






  
06本课总结与验证题

  

    
结构
SQLite 双表 + YAML 清单
topics/messages 两表 + CDR 原始字节，索引支撑随机访问，事务保断电不损。QoS 存在 topics 表的 offered_qos_profiles 列。

    
录制
点名 + 正则是生产标准
-a 磁盘秒爆（还混入 /rosout 等系统话题）；点名圈最小证据集，配双参数压缩、--max-bag-size 分片、--max-cache-size 缓冲。停止一律用 Ctrl+C（优雅写盘），kill -9 会丢缓存并损坏 SQLite。

    
回放
改节奏不改时间戳
-r 倍速、--loop 循环、--start-offset 跳段、--topics 选话题（无 -t）；TF 静态必 loop。回放结束 Publisher 销毁属正常。

    
离线流
--clock（约40Hz）+ use_sim_time
play 带钟、节点与 rviz 认钟、Time 面板验钟——三步跑通"把现场带回工位"。验钟要用带 header 的话题。

  

  
三问一句话收束
  
是什么：把话题的时间序列 + CDR 字节录进 SQLite 双表，配一份 metadata.yaml 清单。

  为什么：现场故障只来一次，数据流过即消失。录下来才能把"去现场"变成"回工位"，把一次性调试变成可重复回归。

  怎么用：record（点名 + timeout + 可选压缩）→ info（用真实 Duration 心算频率验完整性）→ play（-r / --topics / --start-offset / --clock）。三条硬规则：限时用 timeout 不用 -u；选话题用 --topics 不用 -t；压缩必须 mode + format 双参数。

  

  
✎ 验证题（改动型 · 做完对照得分点）——答案需动手执行后用自己的话归纳，参考答案点击展开。

  

    验证题
    
Q1（覆盖目标① 存储）把 metadata.yaml 移出 bag 目录另存，分别跑 ros2 bag info exp16_full 与 ros2 bag play exp16_full，记录现象；再把 yaml 放回，对比恢复情况。由此说清 yaml 与 .db3 各自承担什么。

    
参考答案与得分点
    移走后 info 报找不到/读不出（bag"失忆"，因 rosbag2 先读清单才能定位文件），play 同样无法回放；放回后 info/play 全部恢复（.db3 数据本体完好）。得分点：①现象对比如实（2 分）；②说清 yaml=清单/索引入口、db3=消息本体（4 分）；③结论"两者缺一不可"（2 分）。

    注意：在副本上做，实验后还原，不要在唯一拷贝上试删除。


    
Q2（覆盖目标② 命令）同一段现场，分别用 ①timeout 15 ros2 bag record -a -o bagA、②ros2 bag record /chatter -o bagB --max-bag-size 2048 录制，用 ros2 bag info 对比两包的话题列表与体积；再解释：为什么②的 --max-bag-size 2048 没有产生分片文件？

    
参考答案与得分点
    ①bagA 含 4 个话题（/chatter /rosout /parameter_events /events/write_split），bagB 只有 /chatter——全量 vs 点名的直接证据；②bagB 体积远小于 bagA。不分片原因：--max-bag-size 单位是字节（2048B），且写满才切分——/chatter 1Hz 小消息 15 秒远达不到阈值时按需处理，小数据量下即便超过字节阈值也以实际写入为准、静默无提示。得分点：①对比表完整（3 分）；②单位=字节（3 分）；③"写满才切、无提示"（2 分）。


    
Q3（覆盖目标② 回放）用 ros2 bag info exp16_full 读出 Duration=13.5s、/chatter Count=14，心算频率并判断数据是否完整；然后不改包内容，只用参数让回放"每 0.5 秒收到一条"，验证你的参数确实生效且消息内 stamp 没变。

    
参考答案与得分点
    频率 = 14/13.55 ≈ 1.03Hz，与 talker 标称 1Hz 一致 → 完整（若拿 15s 当分母得 0.93Hz 会误判）。要让间隔从 1s 变 0.5s 用 ros2 bag play exp16_full -r 2.0。验证 stamp 不变：对比前后输出或用 ros2 bag play --dump/echo 观察消息时间字段——-r 只缩放发布节奏。得分点：①心算与分母正确（3 分）；②-r 2.0（3 分）；③"改节奏不改 stamp"（2 分）。


    
Q4（覆盖目标③ 数据集设计）现场录了 15 个话题共 10 分钟的包，要在 3 版导航算法上做回归测试。请重新设计一份最小证据链录制命令：圈出必录话题、加上分片与命名，说明每个参数防的是什么风险；并写出"每次改完自动跑一轮"的验证流程骨架（离线回放 → 自动判定 → 结果留存）。

    
参考答案与得分点
    示例：ros2 bag record /scan /odom /tf /cmd_vel -e "scan|odom" -o nav_reg_001 --max-bag-size 2147483648——感知+定位+控制闭环即最小证据链；-o 可读命名防"时间戳考古"；--max-bag-size 字节单位分片防单文件过大。流程骨架：play --clock + 节点 use_sim_time ← 回放；解析输出/比对轨迹 ← 自动判定；bag+日志+版本号归档 ← 留存。得分点：①话题选择理由（3 分）；②三个参数各防一险（3 分）；③三段式流程闭环（2 分）。


    
Q5（覆盖目标④ 离线联调）按图 16-4 把双开关流程跑通后，故意做一个改动：停掉 --clock（另开一个不带钟的 play）但 rviz2 仍保持 use_sim_time:=true，观察 Time 面板与 TF 现象；再用 ros2 topic delay /chatter 与 ros2 topic delay /scan 分别验证，解释两条命令输出差异的根源。

    
参考答案与得分点
    无 /clock 时：Time 面板停住/为 0（或不推进），节点与 rviz 的 now() 拿不到仿真时间，TF 出现 LookupException/数据过期丢弃（now=今天·stamp=昨天）。delay /chatter 报 msg does not have header（String 无 header 字段），delay /scan 返回小正值=对齐良好。得分点：①停钟现象描述（3 分）；②双开关"缺一不可"结论（3 分）；③无 header 根源（2 分）。
