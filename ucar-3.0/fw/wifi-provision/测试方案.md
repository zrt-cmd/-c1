# XFLZ WiFi 配网服务 测试方案

- 被测版本：`1.0.0`（本仓库 `fw/wifi-provision`；实际运行路径由 `install.sh` 按安装目录生成，
  用 `systemctl show -p ExecStart --value wifi-provision` 确认）
- 对应需求：`需求文档.md`
- 测试类型：真机手工测试（黑盒为主，日志白盒辅助）
- 执行前提：**必须通过串口/本地终端操作**，测试会占用并断开 wlan0

---

## 一、测试范围与策略

### 1.1 被测对象

| 模块 | 文件 | 职责 |
|---|---|---|
| 入口 | `bin/wifi-provision` | 装配 Config/ApManager/Monitor/WebServer，接管 SIGTERM/SIGINT |
| 配置 | `lib/config.py` | 读取 `/etc/xflz/wifi-provision.conf`，内置默认值 |
| 网络 | `lib/ap_manager.py` | nmcli 封装：起停 AP、连接 STA、扫描/重连已存配置 |
| 状态机 | `lib/monitor.py` | `sta_retry → steady → ap_mode → connected` 四态调度 |
| 门户 | `lib/web_server.py` | Flask 配网页 + captive portal 兜底重定向 |

### 1.2 状态机速查（判定日志时的参照）

```
启动 → sta_retry ──(无已存 profile)──────────────────────────────→ ap_mode
                 ├──(等待 NM 自动连接，boot_grace_seconds 内成功)──→ connected
                 ├──(超时后本服务亲自重试，sta_retry_seconds 内成功)→ connected
                 └──(两段都用尽)──────────────────────────────────→ ap_mode

ap_mode ──(收到网页提交)── 成功 ─────────────────────────────────→ connected
                        └─ 失败 → ap_mode（携带 last_error）
ap_mode ──(scan_back 命中已知网络)──────────────────────────────→ connected
           需 scan_interval_seconds>0，且无人占用热点：
           无客户端 DHCP 租约、配网页最近 scan_back_idle_seconds 内无人访问

connected ──(掉线 ≥ disconnect_threshold_seconds)→ steady
          ──(steady 内 NM 宽限 + 主动重试都失败)─────────────→ ap_mode
          ──(恢复连上)──────────────────────────────────────→ connected
```

> `sta_retry` 的两段是**串行**的，用户等配网热点出现的时间是
> `boot_grace_seconds + sta_retry_seconds`，不是其中之一。

### 1.3 测试策略

1. **真机闭环**：以「手机（客户端）+ 真机 wlan0 + NetworkManager」为完整闭环，逐条对应需求验证。
2. **不备份，凭据先留底**：本方案不做配置备份，删掉的连接不会自动还原。
   执行任何删除动作前先做 P1，把正确 SSID/密码记下来，否则设备只能重新配网。
3. **证据驱动**：每条用例必须留存①带时间戳的日志片段 ②`nmcli` 命令输出 ③手机端截图（B/C/E 组）。缺证据不计通过。
4. **两轮计时**：先用「快测配置」跑通全部用例（缩短等待），再用「生产配置」对 P0 用例复跑一次确认时间参数。
5. **测试监控脚本**：本方案配套 `test.sh`，负责设备侧动作与状态展示，手机端操作由人工完成：

   ```bash
   sudo bash test.sh              # 重启服务 → 显示状态 → 删旧配置 → 实时监控
   sudo bash test.sh --cleanup    # 只做收尾（停服务 + 清掉配网热点）
   ```

   脚本做的四件事：
   1. 关掉旧的服务进程，用当前代码重新起一个；
   2. 打印 wlan0 当前的模块状态（服务进程 / wlan0 / IP / 热点 / 已存配置 / 状态机 / 上次错误）；
   3. 如果还有旧的 WiFi 连接配置，列出后问你确认，删掉并盯着它是否自动回到 AP 模式；
   4. 进入**实时监控**，持续显示当前模式（`STA 已联网` / `AP 配网` / `切换中`），
      并过滤出关键日志：状态机切换、手机提交、连接失败、连上热点、热点开关、掉线容忍。

   脚本只负责把状态和日志摆出来，**不做自动判定、不产出报告**；
   手机侧现象（是否弹窗、页面内容、错误提示、拿到的 IP）与最终结论全部由人工确认。

### 1.4 明确不在本次范围

- 射频性能（吞吐、覆盖距离、多客户端并发数）
- 5GHz AP 能力（代码固定 `802-11-wireless.band bg`，即 2.4GHz）
- 配网安全（开放热点无认证、门户无鉴权、可被任意人配网）——仅作为已知情况记录，不作为缺陷上报

### 2.2 P 组 · 前置步骤（按序执行）

**P1 记下正确凭据（硬前置，不可跳过）**

测试从 P5 起会删除 `YY_1-108`，且**不做任何备份** —— 删掉之后设备就忘了这个 WiFi，
想连回来只能重新走一次配网。所以动手删之前，先把正确的「SSID / 密码」记下来，
C1（用正确凭据配网成功）和 E1（用正确 SSID 配错密码）都要靠它：

```bash
sudo grep -E '^(ssid|psk)=' \
  /etc/NetworkManager/system-connections/YY_1-108.nmconnection
```

> 这个密码只有这一份，删掉就没了。如果你不知道它、也没别处能查到，
> 动手前先跟管理员确认；本方案不提供还原手段。

**P2 停用 systemd 服务**（避免与手工运行抢占 wlan0）

```bash
sudo systemctl stop wifi-provision
sudo systemctl disable wifi-provision
systemctl is-active wifi-provision   # 期望输出 inactive
```

**P3 准备快测配置**（缩短等待时间，用于首轮全量）

```bash
sudo tee /tmp/wp-test.conf >/dev/null <<'EOF'
[general]
wifi_interface = wlan0
ap_ssid_prefix = XFLZ
log_level = DEBUG

[timing]
boot_grace_seconds = 6
sta_retry_seconds = 5
per_profile_attempt_seconds = 3
disconnect_threshold_seconds = 10
connect_attempt_timeout = 15
scan_interval_seconds = 0
scan_back_window_seconds = 10
scan_back_idle_seconds = 30

[web]
bind_host = 0.0.0.0
bind_port = 80
EOF
```

> 快测配置里 `scan_interval_seconds = 0` 是**故意**的：回扫会短暂关掉热点，
> 会干扰 A/B/C/E 各组的观察。只有 G1 需要打开它（G1 里单独改）。

验收轮改用生产配置 `/etc/xflz/wifi-provision.conf`，其 `[timing]` 依次为
`boot_grace_seconds=30` / `sta_retry_seconds=15` / `per_profile_attempt_seconds=5` /
`disconnect_threshold_seconds=10` / `connect_attempt_timeout=20` /
`scan_interval_seconds=180` / `scan_back_window_seconds=10` / `scan_back_idle_seconds=60`。

> 注意 `boot_grace_seconds` 在本版本之前是**死配置**（代码不读），现在才真正生效。

**P4 前台运行服务**（便于实时观察日志）

```bash
cd <仓库>/fw/wifi-provision
sudo WIFI_PROVISION_CONF=/tmp/wp-test.conf \
     python3 -u ./bin/wifi-provision \
     2>&1 | tee /tmp/wp-<用例编号>.log
```

> 必须 `sudo`：绑定 80 端口 + 操作 NetworkManager 均需 root。
> 需用 systemd 验证时：`sudo WIFI_PROVISION_CONF=... systemctl start wifi-provision && sudo journalctl -u wifi-provision -f`

**P5 制造「无历史配置」状态**（A 组/D2 前置）

设备上现在有**两个**已存 WiFi（`YY_1-108`、`mimi`），要全删干净才算「无历史配置」：

```bash
sudo nmcli connection delete YY_1-108
sudo nmcli connection delete mimi
nmcli -t -f NAME,TYPE connection show | grep 802-11-wireless   # 期望无输出
```

> 删掉就没了，后面靠 C1 重新配网恢复。`mimi` 的密码是可自助重建的测试热点；
> `YY_1-108` 的密码见 P1。

**P6 制造「有配置但不可达」状态**（D2 前置）

创建一条指向不存在 SSID 的配置，可稳定复现「搜不到旧 WiFi」：

```bash
sudo nmcli connection add type wifi con-name NoSuchNet ssid NoSuchNet
nmcli -t -f NAME,TYPE connection show | grep 802-11-wireless   # 期望有 NoSuchNet
```

清理：`sudo nmcli connection delete NoSuchNet`

### 2.3 日志观测速查

常用日志关键字（状态切换必打 `state: X -> Y`）：

| 关键字 | 含义 |
|---|---|
| `monitor started, state=` | 服务启动，初始态必为 `sta_retry` |
| `no saved WiFi profile, entering AP mode directly` | 无配置，直进 AP |
| `saved WiFi [...]; NM grace Ns, retry window Ns` | 进入开机等待；**方括号里的顺序就是遍历顺序**，D3 靠它取证 |
| `connected to <SSID>` | 第一段结束：NM 自己连上了 |
| `NM did not connect within Ns, driving saved profiles` | 第一段结束：NM 没连上，转第二段主动重试 |
| `reconnect to <SSID> did not connect: <原因>` | 单个 profile 主动重试失败（**不再静默**，旧版本无此行） |
| `STA retry window expired, entering AP mode` | 两段都用尽，切配网 |
| `AP up: <SSID> (open)` | 热点已起 |
| `AP already active:` | `start_ap()` 幂等命中 |
| `AP start failed (attempt N/3), cleaning up wlan0 and retrying` | AP 启动失败重试 |
| `AP unavailable, retrying in 10s` | 3 次全失败 |
| `web server up on` / `web server down` | 门户起停 |
| `user requested connect to <SSID>` | 收到网页提交 |
| `forcing wlan0 disconnect before AP restart` | 连接失败后的清理 |
| `station dropped, holding off AP for Ns` | 掉线容忍窗口开始 |
| `station down for Ns` → `steady: retrying [...] (NM grace Ns, window Ns)` | 进入 steady |
| `steady: still down, entering AP mode` | 切回配网 |
| `steady: no saved profile left, entering AP mode` | steady 时已无任何已存 profile |
| `scan-back: pausing AP for Ns` / `scan-back: reconnected to` | 后台扫描回连 |
| `scan-back skipped: a client is connected to the AP` | 有手机连着热点，本轮跳过（防打断配网） |
| `scan-back skipped: config page opened Ns ago` | 有人正在配网，本轮跳过 |

### 2.4 观测命令速查

```bash
# 当前活动连接（判断 AP 是否在跑）
nmcli -t -f NAME,DEVICE,TYPE connection show --active

# wlan0 状态与地址
nmcli -t -f DEVICE,STATE,CONNECTION device
ip -4 addr show wlan0 | grep inet

# wlan0 详细信息（无 iw 时的替代手段）
nmcli device show wlan0 | grep -E 'GENERAL.STATE|GENERAL.CONNECTION|IP4.ADDRESS'

# 已存 WiFi 配置
nmcli -t -f NAME,TYPE connection show | grep 802-11-wireless

# 门户运行状态（设备侧或手机浏览器侧）
curl -s http://192.168.100.1/status.json
```

### B 组 · 自动弹出配网页（需求一.2）★最高风险，优先执行

> 结论先行：弹窗能否成立取决于 **AP 模式下 DNS 是否把探测域名解析到 192.168.100.1**。NM 的 `ipv4.method shared` **默认不做** DNS 劫持，未知名会返回 NXDOMAIN，探测请求到不了本机门户。
> 本机已放置 `/etc/NetworkManager/dnsmasq-shared.d/xflz-captive.conf`（`address=/#/192.168.100.1`）来弥补这一点，因此 **B2 的目的不是"发现问题"，而是确认这份配置确实被 NM 拉起的那份 dnsmasq 加载生效**——这是最容易被误判成"通过"的一环，必须实做。

#### B1 手机连上后自动弹出门户

- 前置：A1–A4 完成；手机已忘记该 SSID 的历史记录
- 操作：手机连接 `XFLZ-E23ECE`
- 预期：Android 通知栏出现「登录到网络」并可点开；iOS 自动弹出 Captive Network Assistant
- 证据：shot（弹窗出现 / 未出现均需截图）
- 失败时的判据：记录手机型号 + 系统版本 + 是否出现「无网络连接」提示

#### B2 【根因】DNS 劫持是否真正生效 ★P0

- 前置：A2 完成（AP 已起）
- 操作（设备侧，`nslookup`/`dig` 未安装，用 `host`）：
  ```bash
  host captive.apple.com 192.168.100.1
  host connectivitycheck.gstatic.com 192.168.100.1
  host www.msftconnecttest.com 192.168.100.1
  host a-random-nonexistent-domain-xyz.com 192.168.100.1
  ```
- 预期：四个域名**全部**解析到 `192.168.100.1`（第 4 个证明是通配劫持而非只配了特定域名）
- 同时确认劫持配置确实存在且被加载：
  ```bash
  cat /etc/NetworkManager/dnsmasq-shared.d/xflz-captive.conf
  ps aux | grep -E 'dnsmasq.*shared' | grep -v grep   # 确认 NM 拉起的 dnsmasq 进程
  ```
- 结果分三种，判定不同：
  - 全部解析到配网地址 → **通过**，B1 成立有根因支撑
  - 返回 NXDOMAIN / 超时 → **不通过**：需求一.2「自动弹出配网网页」不成立，根因是 DNS 未劫持
  - 劫持配置缺失（如重新刷机后）→ **不通过**，按下方补齐
- 补齐方式（若配置缺失）：
  ```bash
  sudo mkdir -p /etc/NetworkManager/dnsmasq-shared.d
  echo 'address=/#/192.168.100.1' | \
    sudo tee /etc/NetworkManager/dnsmasq-shared.d/xflz-captive.conf
  sudo systemctl restart NetworkManager
  ```
- 证据：命令输出（修复前 / 修复后各一份）

#### B3 三个平台的探测 URL 行为

- 前置：A2 完成
- 操作（设备侧，模拟各平台探测）：
  ```bash
  curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' \
       http://192.168.100.1/generate_204
  curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' \
       http://192.168.100.1/hotspot-detect.html
  curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' \
       http://192.168.100.1/connecttest.txt
  curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' \
       http://192.168.100.1/nonexistent/path
  ```
- 预期：全部返回 `302` 且 `redirect_url` 为 `http://192.168.100.1/`（`catch_all` 兜底）
- 判定说明：302 → `/` → 200 会让 Android/iOS 判定为 captive portal 从而弹窗，**这是可接受的实现**；但需 B2 的 DNS 配合
- 证据：命令输出

#### B4 手动兜底可访问

- 前置：手机已连热点
- 操作：手机浏览器访问 `http://192.168.100.1`
- 预期：正常渲染「设备配网」页面
- 证据：shot

#### B5 页面内容正确

- 前置：B4 完成
- 操作：查看页面文案；再触发一次失败（E1）后重新连接查看
- 预期：显示当前热点名 `XFLZ-E23ECE`；`last_error` 非空时顶部出现「上次连接失败：…」
- 证据：shot

### C 组 · 提交凭据并切换 STA（需求一.3、一.4）

> 目标 WiFi 建议用 `YY_1-108`（P1 已读出正确密码），这样 C1 成功即等于恢复了设备原网络。
> 若需开放网络用例，用路由器访客网络或手机热点（安全类型设为「无」）。

#### C1 正确密码 → 关 AP 切 STA ★P0

- 前置：A1–A4 完成，服务运行中，已连手机
- 操作：手机门户填入 `YY_1-108` + 正确密码 → 提交
- 预期（按顺序）：
  1. 手机跳转到「正在连接」页
  2. `web server down` → AP 消失（手机 WiFi 断开，属正常）
  3. 日志 `connected to YY_1-108`

### D 组 · 开机与后台逻辑（需求二）

#### D1 有历史配置 → 优先 STA 重连，不进 AP ★P0

- 前置：P1 已完成；`YY_1-108` 配置存在且已连上（`sudo nmcli connection up YY_1-108` 后确认在线）；服务停止

- 预期：日志 `saved WiFi [...]; NM grace Ns, retry window Ns` 后很快 `connected to <SSID>`
  → `state: sta_retry -> connected`；**全程不出现 `AP up:`**
  - 这条走的是第一段（NM 自己连），应远快于 `boot_grace_seconds`
- 证据：log

#### D2 有配置但全部不可达 → 等待后自动切 AP ★P0

- 前置：P6 完成（存在 `NoSuchNet`），且其它已存 WiFi 均不在信号范围内
- 操作：
  ```bash
  date '+%F %T'            # 记录启动时刻
  # 启动服务
  ```
- 预期：日志依次出现
  1. `saved WiFi [...]; NM grace Ns, retry window Ns`
  2. `NM did not connect within Ns, driving saved profiles`
  3. `STA retry window expired, entering AP mode` → `AP up:`
  - 「启动时刻」到第 3 条的时间 ≈ `boot_grace_seconds + sta_retry_seconds`，误差 ≤ +5s
  - 生产配置 ≈ 30 + 15 = 45s；快测配置 ≈ 6 + 5 = 11s
- 证据：log（带 `%(asctime)s` 时间戳）+ 手工记录的启动时刻

#### D3 排在前面但搜不到的网络，不得挡住后面能连的网络 ★P0

- **背景**：这是本版本修掉的核心缺陷。旧逻辑把 `sta_retry_seconds` 当成**所有 profile 共享**的
  预算，排在前面但不在范围内的那个 profile 会把预算吃光，导致后面的 profile **一次都没被试**——
  设备明明停在一个已保存网络旁边，却仍然掉进 AP 模式。
  真实场景：房间 A 连过 `YY_1-108`，换到房间 B 配了 `mimi`，重启后连不上 `mimi`。
- 前置：准备两个已存 profile，**让不在范围内的那个排在前面**：
  ```bash
  # 1. 造一个搜不到的网络
  sudo nmcli connection add type wifi con-name AAA-NoSuchNet ssid AAA-NoSuchNet
  # 2. 接上真实网络，使其进入已存列表
  sudo nmcli connection up YY_1-108
  ```
- 操作：启动服务
- 预期：
  1. 启动日志 `saved WiFi [...]` 里 **`AAA-NoSuchNet` 排在 `YY_1-108` 前面**
     （若顺序不符，改个名字再试，直到它排前面为止）
  2. 出现 `reconnect to AAA-NoSuchNet did not connect: ...` —— 证明它试过、失败了、
     **没有把预算吃光**
  3. 紧接着出现对 `YY_1-108` 的尝试并 `connected`
  4. **全程不出现 `AP up:`**
- 判定：若日志停在 `STA retry window expired` 而**没有**对 `YY_1-108` 的 `reconnect to`，
  即为旧缺陷复现，本轮不通过
- 清理：`sudo nmcli connection delete AAA-NoSuchNet`
- 证据：log（需能看出两个 profile 的尝试先后）

#### D4 `Restart=always` 生效

- 前置：服务通过 systemd 运行
- 操作：`sudo kill -9 $(systemctl show -p MainPID --value wifi-provision)`，随后 `systemctl is-active wifi-provision`
- 预期：5s 内（`RestartSec=5`）自动拉起为 `active`
- 证据：命令输出 + `journalctl -u wifi-provision -n 30`

#### D5 运行中断网 → 自动切回配网

- 前置：服务处于 `connected` 态
- 操作：关闭目标 AP（关路由器 / 关手机热点）
- 预期：日志 `station dropped, holding off AP for Ns` → `station down for Ns` → `state: connected -> steady`
  → `steady: retrying [...] (NM grace Ns, window Ns)` → `steady: still down, entering AP mode` → `AP up:`
- 实测耗时口径：`disconnect_threshold_seconds`（connected 里折算掉线）
  \+ `disconnect_threshold_seconds`（steady 里等 NM）
  \+ `sta_retry_seconds`（主动重试兜底），生产配置约 10 + 10 + 15 = **35s**
- 判定：确认真实耗时并对照需求「断网超时自动切配网」是否可接受；
  若不可接受，调这三个参数，或改设计（缩短/合并等待段）
- 证据：log（含时间戳，需算出实测秒数）

#### D6 短暂断网不立刻切 AP

### G 组 · 边界与缺陷探测

#### G1 后台 scan-back（默认开启，且不得打断配网）

本版本把 `scan_interval_seconds` 的默认值从 `0`（关闭）改为 `180`（开启）：
旧行为下一旦进了 AP 模式就永远出不来，只能人工重新配网。代价是回扫期间热点会短暂消失，
所以加了"没人在用"的前置条件。本节两种情况都要走。

- 前置：`scan_interval_seconds = 60`（便于观察）、`scan_back_window_seconds = 10`

**G1-1 无人使用时应当回扫**

- 操作：进入 `ap_mode`；手机**不要**连热点，也不要打开配网页
  （若之前连过，先断开并等待超过 `scan_back_idle_seconds` 再观察）
- 预期：日志 `scan-back: pausing AP for 10s`，AP 与门户一起消失约 10s 后恢复
  - 命中已知网络：`scan-back: reconnected to <名称>` → `connected`
  - 未命中：`scan-back: no known network, restoring AP`
- 不发回扫时的排查：确认 `saved_wifi_profiles()` 非空（没有已存网络时按设计不回扫）

**G1-2 正在配网时不得回扫（本版本新增的保护）**

- 操作：手机连上热点并打开配网页，**保持连接、页面不做任何操作**
- 预期：到时间点后**不出现** `scan-back: pausing AP`，而是出现
  `scan-back skipped: a client is connected to the AP`
  或 `scan-back skipped: config page opened Ns ago`；**热点全程不消失**
- 反向确认：观察期间 `ip -4 addr show wlan0` 应一直含 `192.168.100.1`，
  手机侧不应出现掉线/重连
- 判定：热点被抽走 → 保护失效，按缺陷上报

- 证据：log + 手机端连通性变化截图 + `ip -4 addr show wlan0`

#### G2 配网成功后重启设备不回 AP ★P0

- 前置：C1 成功（设备已连上目标 WiFi）
- 操作：`sudo reboot`，开机后观察
- 预期：服务自动启动并直接 STA 重连，**不出现配网热点**
- 证据：log（`journalctl -u wifi-provision -b`）+ 手机 WiFi 列表截图

#### G3 配网后 profile 属性正确

- 前置：C1 成功
- 操作：
  ```bash
  nmcli -t -f NAME,TYPE,AUTOCONNECT connection show | grep 802-11-wireless
  ```
- 预期：profile 名 = SSID，`autoconnect` 为 `yes`
- 证据：命令输出

#### G4 残留 AP profile 的清理

- 前置：手工造一个残留：`sudo nmcli connection add type wifi ifname wlan0 con-name xflz-provision-ap ssid leftover`
- 操作：正常启动服务进入 `ap_mode`
- 预期：`start_ap()` 先 `connection delete xflz-provision-ap` 再重建，最终只有一个 AP profile 且 SSID 正确
- 证据：命令输出 + log

#### G5 端口 80 被占用时的行为 ★建议新增

- 前置：先占用 80 端口：`sudo python3 -m http.server 80 &`
- 操作：启动服务，进入 `ap_mode`
- 预期（**预期为暴露缺陷**）：`web.start()` 抛 `OSError` → 被 `Monitor.run()` 的 `except` 捕获 → `log.exception` + `sleep(2)` → 重进 `_do_ap_mode` → 再抛，形成 **2 秒一次的无限崩溃循环**，门户永远起不来，且该状态下 scan-back 逻辑也不会执行
- 判定：确认是否复现该循环；若复现即为缺陷，修复方向是让 `web.start()` 失败可上报/可降级，而非静默重试
- 证据：log（观察异常堆栈重复出现）

#### G6 配置无校验的边界值

- 前置：服务停止
- 操作：分别设置 `boot_grace_seconds = 0`、`sta_retry_seconds = 0`、
  `per_profile_attempt_seconds = 0`、`scan_back_window_seconds = 0`、
  `connect_attempt_timeout = 0` 各跑一次
- 预期：行为可预期且不崩溃——`boot_grace_seconds = 0` 表示不等 NM 直接进第二段；
  `sta_retry_seconds = 0` 表示立即判失败切 AP；`per_profile_attempt_seconds = 0`
  会被下限钳到 1s；不得出现 100% CPU 空转或异常刷屏
- 证据：log + `top -b -n1 | grep python`

## 四、关键风险与预判缺陷

执行前先读本节。以下问题来自代码静态分析 + 本机实测，测试时需逐条确认并留存证据。其中 **D-4 已在真机实测确认**（用临时配置 `test:colon` 验证后已删除，未留下残留），其余为待确认的预判。

| 编号 | 问题 | 影响 | 对应用例 | 修复方向 |
|---|---|---|---|---|
| D-1 | **门户 DNS 劫持依赖仓库外的文件**：`/etc/NetworkManager/dnsmasq-shared.d/xflz-captive.conf`（`address=/#/192.168.100.1`）已存在并生效，但本项目仓库与安装流程中**都没有该文件的来源** | 重新刷机 / 换板部署后「自动弹出配网网页」会静默失效，现场表现为「手机连上了但没网」，很难定位到根因 | B1、B2 | 把该文件纳入项目（如 `deploy/`）并在安装步骤中落盘，或改由 `lib/ap_manager.py` 在 `start_ap()` 时确保其存在 |
| D-2 | **掉线到重开 AP 是三段相加**：`_do_connected` 折算掉线 + `steady` 等 NM 自动连接 + 主动重试兜底 | 生产默认约 10 + 10 + 15 = **35s** 才切配网，与需求「断网超时自动切配网」的直觉不符 | D5 | 明确需求预期；如需更短，调小这三个参数，或合并等待段 |
| D-3 | **端口 80 被占用 → 无限崩溃循环**：`web.start()` 的 `OSError` 被 `run()` 兜底 `except` 吞掉，2s 后重进同一状态再抛一次 | 门户永久不可用且无有效告警，AP 模式还丧失 scan-back | G5 | 区分「可恢复错误」与「配置/资源错误」，后者应上报并退出或显著告警 |
| D-4 | **`nmcli -t` 冒号未转义（已实证确认）**：`saved_wifi_profiles()` 已用 `rpartition` 正确规避，但 `current_connection()` 与 `disconnect()` 仍用 `split(":")`（均在 `lib/ap_manager.py`）。实测 nmcli 1.36.6 对名为 `test:colon` 的配置输出 `test\:colon:802-11-wireless`，`split(":")` 得到 `['test\\', 'colon', '802-11-wireless']` | SSID 含冒号时字段错位：日志打错连接名，`disconnect()` 可能漏断或断错配置 | C4 | 统一为 `re.split(r'(?<!\\):', line)`，或统一采用 `rpartition` 风格 |
| D-5 | ✅ **已修复** —— 原缺陷：同 SSID 错误密码会删掉原本可用的配置（`connect()` 先 `nmcli connection delete <ssid>`，失败后不重建）。现改为：已存在的 profile **原地** `connection modify` 改密码再 `down`/`up` 重新激活，失败则**回滚到原密码**；只有本次新建的 profile 才删除 | 用户误输一次密码，原来可用的配置被清除，设备下次开机直进 AP 配网 | E1 | 已修复（`lib/ap_manager.py` `connect()` / `_undo_failed_connect()`） |
| D-6 | **`_friendly_error` 匹配顺序**：`"not found"` 判断早于 `"secrets were required"`，含 "not found" 的密码错误信息会被误报为「SSID 不存在」 | 用户看到的错误提示指向错误方向，无法自助修复 | E1、E2 | 调整判定顺序，或改为按 nmcli 错误码 / 更精确的模式匹配 |
| D-7 | **AP 固定 2.4GHz**（`802-11-wireless.band bg` 硬编码），且 `iw`/`hostapd` 未安装，AP 行为无法用标准工具核查 | 无法切 5GHz；验证手段受限 | A2 | 视需求决定是否增加配置项 |
| D-8 | **配置无校验**：负数、非数字、极端值行为未定义 | 现场改配置易触发不可预期行为 | G6 | 加载时做范围校验并对非法值回退默认 + 告警 |
| D-9 | ✅ **本次修复** —— 原缺陷：开机 `_do_sta_retry` 一进函数就用**共享预算**遍历 profile，排在前面但不在范围内的网络会把 `sta_retry_seconds` 吃光，后面的 profile 一次都不会被试。实测真机日志显示 `mimi` 在整个重试窗口内从未出现激活记录（NM 日志里只有另一个网络的反复 `Activation: starting`），设备旁边就是可用网络却掉进 AP 模式。现改为：先让 NM 按扫描结果自己连 `boot_grace_seconds`，超时后才按 `per_profile_attempt_seconds` **给每个 profile 独立时间片**重试，且 NM 正在激活时不打断 | 换房间/换网络后重启连不上新网络，必须人工重新配网 | D3 | 已修复（`lib/monitor.py` `_do_sta_retry`/`_active_retry`、`lib/ap_manager.py` `reconnect_saved`） |
| D-10 | ✅ **本次修复** —— 原缺陷：`scan_interval_seconds` 默认 `0`，回扫全程关闭，一旦进了 AP 模式就再也出不来；且回扫在**配网过程中**也会触发，把正在填表单的用户踢下线 | 一次偶发失败 = 永久卡在 AP；或配网配到一半热点消失 | G1 | 已修复：默认改为 `180`，并加"无 DHCP 租约 + 配网页近 `scan_back_idle_seconds` 无人访问"两道门槛 |

## 六、R 组 · 环境恢复清单

测试结束后**必须**执行，使设备回到可用状态。

本方案不做配置备份，所以「回到原网络」靠的是 **C1 用正确凭据配网成功**。
如果 C1 失败、或中途放弃，设备会停在配网 AP 模式，需要重新配一次网。

```bash
# 1. 停止被测服务
sudo systemctl stop wifi-provision
sudo pkill -f 'bin/wifi-provision'

# 2. 清理测试期间产生的连接配置
sudo nmcli connection delete xflz-provision-ap 2>/dev/null
sudo nmcli connection delete NoSuchNet 2>/dev/null
sudo nmcli connection delete AAA-NoSuchNet 2>/dev/null   # D3 造的

# 3. 确认网络状态（应已连上范围内那个真实网络：房间 A 是 YY_1-108，房间 B 是 mimi）
nmcli -t -f DEVICE,STATE,CONNECTION device | grep '^wlan0:'
ip -4 addr show wlan0 | grep inet          # 期望拿到 192.168.x.x/24
ip route get 1.1.1.1                       # 期望默认路由经 wlan0

# 4. 若第 3 步显示未连接，用正确凭据重新配网（手机连热点提交），或手工：
# sudo nmcli device wifi connect YY_1-108 password '<P1 记下的密码>'
# sudo nmcli device wifi connect mimi    password '<mimi 的密码>'

# 5. 按需恢复开机自启（install.sh 装完即为 enabled，需要保持常驻则跳过）
# sudo systemctl enable wifi-provision
```

**R 组通过判据**：wlan0 恢复为 `connected`（连上哪个网络取决于当时所处的房间）、拿到 IP、默认路由经 wlan0、无残留 `xflz-provision-ap` / `NoSuchNet` / `AAA-NoSuchNet` 配置。

> 若第 5 步失败：检查 `/etc/NetworkManager/system-connections/` 下文件权限是否为 `600`（权限过松 NM 会忽略该配置），并查看 `journalctl -u NetworkManager -n 50`。
